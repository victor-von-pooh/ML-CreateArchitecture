# 設計

ML-CreateArchitecture の今の設計と決まりをまとめる. まだやっていないことは [TODO.md](../TODO.md) に置く.

## 1. 役割と位置づけ

ML-ModelControl の部品を GUI で並べてつなぎ, モデルを組み立てるローカルの Web アプリ. 「機械学習を全て GUI 上で行う」アプリ (問題の設定, データの分析, モデルの作成・選定, モデルの学習・評価, 推論の段階に分けて作る) のうち, 「モデルの作成・選定」の段階の画面.
コードを書かずに, 部品の一覧から選んで置き, 線でつなぎ, 引数をフォームで決め, 形とパラメータ数を確かめながらモデルの定義を作る.

- 今は独立したアプリ. 将来は ML-Found と ML-Dashboard と合わせて, 1 つのアプリに統合することを目指す

| 部分 | 中身 |
| --- | --- |
| バックエンド | Python, FastAPI. ML-ModelControl を呼ぶ API と, 定義のファイルの一覧, 読み込み, 保存. データセットから入力と出力を読む API と, プロジェクトに保存する API (ML-EDA と ML-Quest を通す) |
| 画面 | TypeScript, React, Vite. グラフの編集に React Flow (`@xyflow/react`) を使う |

ML-Dashboard と同じ構成と道具 (uv, pnpm, Ruff, mypy, Prettier, oxlint, OpenAPI から画面の型を作る) にそろえ, 将来の統合を楽にする.

## 2. 使うライブラリと約束

ライブラリは ML-ModelControl (submodule. ML-Dashboard と ML-Found の関係と同じ). ML-EDA と ML-Quest は追加の依存 `project` にし (「データセットとプロジェクト」のダイアログだけで使うため), `make setup` の既定で入れる. 入れていない場合は, その操作で入れ方 (「make setup (EXTRAS を書く場合は project も含める)」) を出す.

- **他の段階のファイルは, その約束を持つライブラリを通して読む**: データセットの説明 (`dataset.yaml`) は ML-EDA, 問題の設定は ML-Quest を通して読み, このアプリは自分では開かない. ML-Inference がデータセットを ML-EDA で読むのと同じ理由で, 版の確かめと読み方を持ち主の 1 か所にまとめ, 約束の版が上がっても読む側を直さずに済むようにするため (知らない版は持ち主の誤りの文で止まる)

- モデルの定義 (YAML か JSON) の読み書き, 確認, 形の推定, 組み立ては全て ML-ModelControl が行う. このアプリは画面と, 定義のファイルの置き場だけを受け持つ
- 定義のファイルの形は決めない. 読み書きするのは ML-ModelControl の定義の形だけで, その形が他の段階 (学習など) との約束になる
- 読み書きするファイル:

| ファイル | 読むか書くか | 約束 |
| --- | --- | --- |
| モデルの定義 (`models/<名前>.yaml`) | 読み書き | ML-ModelControl の定義の形. 版 1 と版 2 を読み, 保存は `dump_spec` が書ける最も低い版で書く (下の「3. 画面」の「パラメータの状態」) |
| 外部の重み (`torch.load` で読めるファイル, safetensors, Hugging Face) | 読むだけ | ML-ModelControl の `build_model` と `weights_report` (下の「4. API」の `POST /api/weights`) |
| 書き出す Python のコード | 書く (コピーかダウンロード) | ML-ModelControl の `export_python`. ML-ModelControl を入れていない環境でも動く |
| データセットの説明 (`dataset.yaml`) | 読むだけ | ML-EDA の約束. `ml_eda.model_inputs` で入力の名前, 形, 型と, タスク, 目的の列, クラス, 正解の種類, 出す値の数を読む (版 1 の列の正解と, 版 2 と 3 のファイルの組 (画像と領域, 撮影か点群と点群). 知らない版と知らない項目の組は ML-EDA の誤りの文を出す) |
| 問題の設定 (ML-Quest の YAML) | 読むだけ | ML-Quest の約束. `load_problem` と `handoff` で, プロジェクトの記録 (`model.project_model_spec`, `project.path`, `data.project_dataset`) を読む. ML-Pathfinder の置き場 (`ML_PATHFINDER_HOME`. 無ければ `~/.ml-pathfinder`) の `problems/<識別子>/problem.yaml` を一覧にする (ML-Fathom の一覧と同じ置き場と読み方) |
| プロジェクトのモデルの定義 (骨組みでは `<プロジェクト>/models/model.yaml`) | 書く | ML-ModelControl の定義の形 (置き場の定義と同じ書き方). 学習のスクリプトが config の `model.spec` から読む |
| 学習の実験の定義の写し (`<実験の置き場>/<名前>/<日付>/<時刻>/model_spec.yaml`) | 読むだけ | ML-Found の実験のディレクトリの形 (ML-Found の `docs/FORMAT.md`). `source.yaml` の `model_spec` の `status` と `sha256` で, 学習を始めたときの定義かを見分ける (下の「3. 画面」の「実験の定義の写しを開く」) |

- 保存した定義は ML-ModelControl の `build_model` で `nn.Module` になり, ML-Found の学習スクリプトから使う

## 3. 画面

1. **部品の一覧** (左): 出どころごとに並べ, 名前と説明で検索する. 使えない部品 (ライブラリが無いものなど) は理由付きで選べない状態にする. 押すと見えている範囲 (か選んでいるものの右) に置き, キャンバスにドラッグすると落とした位置に置く (ドラッグでは線を引かない). 検索欄の Enter で, 使える部品のうち名前が一致するもの, 名前の終わりが一致するもの, 名前に含むもの, 説明に含むものの順に最初の 1 つを置く. 名前と説明のほかに, よく使う呼び方 (`global_mean_pool`, `dense`, `residual` など) でも探せる. 使えない部品の入れ方は `make setup EXTRAS="project ..."` で示す (既定の `project` を外さないため)
2. **キャンバス** (中央): ノード (部品), 入力, 出力を置き, 口から口へ線を引いてつなぐ. ノードには部品の名前, 口, 推定した出力の形, 誤りの印を出す (口の行にマウスを重ねると, 口の名前 (出力は形も) に登録簿の口の説明を付けて出す). 位置は定義の `ui` に保存する. 線とノードは選んで Delete か Backspace で消す. 幅 1536 px 未満の画面ではミニマップを出さない
3. **詳細** (右): 選んだノードの名前, 入力のつなぎ先 (選択の欄. ノードは新しい順. 登録簿に口の説明 (`op.Reparameterize` の `mu` は「平均」など) があれば, 引数の説明と同じく欄の下に出し, 欄の説明として読み上げる), 引数のフォーム (登録簿の説明と範囲付き. 種類と範囲に合わない値はその場で理由を出して反映しない. 選択肢は選択の欄, 真偽値か null だけを受け取る引数 (`Optional[bool]`) は未設定, true, false, null の選択の欄, 値の候補 (`suggestions`) は打ちながら選ぶ欄), 一覧に無い引数 (`extra_params` の部品. 名前を書いて加える), 呼び出すときの設定の値, 入ってくる形 (つなぎ先ごと) と推定した出力の形とパラメータ数, 誤りと注意 (確認の誤りがあるノードは, 計算の誤りの文を重ねて出さない) を出す. 入力を選んだ場合は形, 型, 値の作り方を編集する. 何も選んでいない場合は全体の情報 (パラメータ数と学習するパラメータ数), 定義全体の誤り, 誤りと注意のあるノード (引数の不足, 出力に届かない, つなぎ先が 1 つの足し算など. 押すと選ぶ) と, 形の推定で失敗したノードと出力の一覧を出す
4. **上の操作**: 新規, 開く (保存した定義, 同梱の例と, 学習の実験の定義の写し (下の「実験の定義の写しを開く」). 保存した定義は消せる. 例の説明は数行になる (雛形は学習の step で行うことまで書く) ので, 行の間を空けて全文を出す. 読み上げでは例の名前をボタンの名前, 説明をボタンの説明にする. 部分モデルにする一覧も同じ), 保存 (開いたものと違う名前で既にある定義に保存する場合は確かめる), 元に戻す・やり直す, 整列, 入力と出力の追加, YAML と Python のコードの表示 (コピーとファイルのダウンロード), データセットとプロジェクト (下の「データセットとプロジェクト」), 明るさの切り替え. 保存すると少しの間, 画面の右下に「<名前> に保存しました」と出す (誤りがあれば「誤り n 件のまま」も). 幅 1280 px 未満ではアプリの名前と, 新規, 開く, パラメータ数の文字を隠して (アイコンと数だけにして) 1 行に収める. 全体のパラメータ数と誤りの数 (形の推定の失敗を含む) を出し, 大きすぎて形を推定しない場合は「形は未推定」と出す. 幅 1536 px 未満では整列, 入力, 出力, YAML, Python のボタンを, 幅 1800 px 未満ではデータセットとプロジェクトのボタンをアイコンだけにする

- **学習済みの重みのライセンス**: 学習済みの重みを読める部品 (ML-ModelControl の部品の一覧の `weights_params` が空でないもの. Hugging Face, timm, torchvision, segmentation_models_pytorch など) のノードの詳細に, 部品の説明の下に「学習済みの重みのライセンス」の欄を出す. ライセンスに関わる引数 (重みを読む引数と, モデルの名前, 版, 符号化器の名前と, 名前と版以外で重みを変える引数 (timm の `pretrained_cfg`, `pretrained_cfg_overlay`, `checkpoint_path` など. ML-ModelControl の `WEIGHT_OVERRIDE_PARAMS` に合わせる)) が落ち着いてから (0.6 秒) バックエンドに聞き (他の引数を変えても聞き直さない. 落ち着くまでの間は前の結果を出さず読んでいる途中と出す. ノードを選び直すと前のノードの結果は出さない), ML-ModelControl の `pretrained_info` が配布元 (Hugging Face のモデルの説明など) から読んだライセンス, 商用で使えるか, 説明, どこから読んだか (読めなかったか), 読んだ版, 推論の一式に重みを写せるか, 配布元のページへのリンクを出す. 商用で使えないものは誤りの色, 分からないもの (空, 独自の条件, 申請制, 読めなかった) は注意の色で「警告: …」とする (読み上げは控えめに `role="status"`. ノードを選ぶたびに割り込まないため). 重みを読まない引数 (`pretrained` を外すなど) では「今の引数では学習済みの重みを読みません」と出す. 部品の一覧では, 重みを読める部品の説明 (マウスを重ねた文) に, 置いた後の詳細でライセンスを確かめる案内を足す. 結果はバックエンドが覚え (読めたものは 1 日, 読めなかったものは 10 分), 画面も 10 分は聞き直さない. 非公開と申請制のモデルは, バックエンドを起動する環境の `HF_TOKEN` で読む. 通しのテスト (Playwright) は `HF_HUB_OFFLINE=1` で起動し, ネットワークを使わない
- **パラメータの状態 (定義の版 2)**: ノードの詳細の「呼び出すときの設定」の後に「パラメータの状態」の欄を出す (ML-ModelControl の定義の版 2 の `train`, `eval_mode`, `zero_init`, `weights`, `share`. 書き方と意味は ML-ModelControl の docs/DESIGN.md の「パラメータの状態」). 本体のノードと部分モデルの中のノードのどちらでも使える
    - 「学習する」(既定で入. 外すと `train: false` の凍結) と「評価の形のまま」(`eval_mode: true`. BatchNorm の統計と Dropout も止める. 凍結とは別に選び, 既定は外. 凍結した BatchNorm に書いていない場合は ML-ModelControl の注意 `frozen_norm_stats` を出す) のチェックの欄
    - 零初期化: 「しない」「全てのパラメータ」「名前を選ぶ」(カンマで区切った名前. 例: `weight, bias`. 部分モデルのノードは `nodes.fc.weight`)
    - 共有: 「しない」「ノード全体」(同じ部品のノードから選ぶ. 引数は同じ値を書く) 「パラメータごと」(1 行に `weight = embed.weight`). ノード全体を共有するノードは, 他の状態の欄を出さない (元のノードに従うため)
    - 外部の重み: 出どころ「読まない」「ファイル」(パス. 相対のパスは定義の置き場から) 「Hugging Face」(置き場の名前, ファイル, 版) 「学習済みの部品」(部品の名前と引数の JSON) と, 入れ物のキー (`state_key`), キーの付け替えの並び (1 行ごとに「前置き」か「正規表現 (番号の付け替え)」を選び, 前置き / 正規表現, 置き換え, 足す数 (正規表現だけ). 足す, 消す), 「合わない重みがあれば止める (strict. 既定で入)」のチェック. 既定の strict を欄の名前に出す
    - 「重みを読んで確かめる」ボタン: 定義全体を組み立てて外部の重みを実際に読み (`POST /api/weights`), 読んだノードごとに 読めた / 形の違う / 新しい / 使わない重みの数, 出どころ, ライセンス (Hugging Face と学習済みの部品から読んだ場合. 「学習済みの重みのライセンス」と同じ表示), 形の違うキーと新しいキーと使わないキーの一部を出す. 読めない場合 (ファイルが無い, strict で合わない, 1 つも読めない) は誤りの文を出す. ファイルとネットワークを使い, 重みも作るので, 編集のたびの確認 (`POST /api/check`) では読まず, ボタンを押したときだけ読む
    - 画面の中の定義は今の版 (2) で持ち, 版 2 の項目を使うと版を 2 にする (下書きや版 1 の空の定義に項目を足した場合). 保存と YAML の表示は ML-ModelControl の `dump_spec` が書ける最も低い版で書く (版 2 の項目を使わなければ版 1 のまま. 版 1 だけを読む古い学習のスクリプトでも読める)
    - 「ノード全体」の共有を選ぶと, 引数を元のノードに合わせ, 他の状態の項目を外す (元のノードに従うため). このノードを元に共有しているノードがある場合と, 同じ部品のノードが無い場合は選べない. 複製と写しでは `share` を写さない (別の定義に貼ると元のノードが違うため)
    - 手で書いた定義などで, ノード全体を共有するノードに書けない項目が残る場合は, 誤りの文と「書けない項目を外す」ボタンを出す. パラメータごとに共有するノードの「学習する」には, 共有するパラメータは元のノードの設定に従うと添える
    - 重みの読み込みの報告は, 読んだ後に定義が変わったら出さない (今の定義の報告ではないため). 報告の注意 (共有するパラメータをファイルから読まなかったなど) も出す
    - 版を 2 に上げるのは, 履歴に残す全ての変更 (部分モデルを写す, 1 つのノードだけのものにするなどを含む) と下書きと開いた定義
    - ノードの名前を変えると, 共有の元の名前 (`share` の値) も書き換える (同じ定義の中だけ. 外側のノードの `zero_init` や付け替えに書いた部分モデルの中の名前は書き換えない). 共有の元のノードを消すと, 共有の欄は残り誤り (`invalid_share`) になる (黙って共有を外さないため)
- **実験の定義の写しを開く**: 「開く」のダイアログの「学習の実験の定義の写し」で, ML-Dashboard が候補を順に学習した実験に残る定義の写しを開く. 候補を比べて選んだ定義を, 名前を付けてプロジェクトの `models/` に保存し直すため (定義を書くのはこの画面の役目なので, 学習の画面はプロジェクトのファイルを変えない)
    - プロジェクトのディレクトリか問題の設定のファイル (保存先と同じ決め方でプロジェクトを決める) を書いて「実験を探す」を押すと, 実験を写しの更新の新しい順に並べる (実験, 写した元の定義の場所, `run.json` の状態 (ML-Dashboard と同じく完了, 実行中, 中断, 失敗. 他は未完了), 時刻). 辿るディレクトリは 5000 までで, 超えたら途中までを並べて知らせる (大きな置き場で長く止まらないため). 探した場所はブラウザに覚え, 「プロジェクトに保存」の欄に入れる (続けて保存するため)
    - 実験の置き場は, ML-Dashboard と同じく `configs/default/train.yaml` の `experiment.output_dir` (書いていなければ `outputs`) に, `configs/default/` の他の YAML と `configs/experiment/` の下 (下の階層も) の YAML の `experiment.output_dir` を足したもの (別の config で出力先を変えた実験も探すため). `~` から書いた値はホームに展開する. プロジェクトの中で, 途中にリンクの無い置き場だけを探し, 他 (外, プロジェクトそのもの, 参照か URL) は理由を出して探さない. 実験は `<置き場>/<名前>/<日付>/<時刻>/` で `config.yaml` と `source.yaml` を持つディレクトリ (ML-Found の形). 途中のリンクはたどらない
    - 開けるのは, `source.yaml` の `model_spec` の `status` が `copied` で, `model_spec.yaml` がリンクでない普通のファイル (16 MiB まで) で, 中身の sha256 が記録と合うものだけ. 他は理由を出して選べなくする (学習を始めた後に書き換えた写しを, 学習に使った定義として開かないため). 理由は ML-Found の `status` ごとの文 (`missing`, `outside`, `link`, `not_file`, `unreadable`, `too_large`, `invalid`, `write_failed`), 知らない値は「定義を写していません」, 欄の無い古い記録は「定義の写しの記録がありません」
    - `source.yaml` と `run.json` は, リンクでない普通のファイルを 1 MiB まで読む. 写しは, リンクを辿らずに開いて普通のファイルかを確かめてから 16 MiB まで読む (確かめた後に置き換えられても外を読まないため)
    - 写しが YAML の別名 (`&a` と `*a`) を 1 つでも使う場合と, 入れ子 (辞書と並び) が 100 段を超える場合は, 読む前の字句の段で断って開かない (ML-Dashboard が写しを使う決まりと同じ. 自分を指す別名, 別名を重ねて膨らむ定義, 深い入れ子で長く止まらないため)
    - 開けなかった誤りは, 実験の欄の中に出す
    - 開くと, 同梱の例と同じく保存していない名前の付いた定義になり (保存する名前の候補は写した元の定義の名前. 写しから起動し直した実験は実験の名前), 部品の一覧の上に「プロジェクトに保存」で保存できることを出す. 保存は今の流れのまま (既にあるファイルは確かめてから上書きする)
- **データセットとプロジェクト**: ML-EDA (ML-Fathom) で書き出したデータセットと, ML-Quest (ML-Pathfinder) で書き出した学習のプロジェクトにつなぐ. 値をファイルから写し取る手間と写し間違いを無くすため. 上の操作の「データセットとプロジェクト」のダイアログに, 次の 3 つの欄を並べる
    - 「問題の設定から選ぶ」: ML-Pathfinder の置き場の問題の設定を, 更新の新しい順に並べる (名前, プロジェクトの場所, 更新時刻). 押すと, その problem.yaml を下の「プロジェクトに保存」の欄に入れて保存先を確かめ, 記録のデータセットの場所を「データセットから入力と出力を作る」の欄に入れる (欄に打った後でも入れる. 選んだ問題の設定のものにそろえるため). プロジェクトの場所を打たずに, 問題の設定から入力と出力を作って保存できるようにするため
        - 使えるのは, 保存先を「プロジェクトに保存」と同じ決め方で決められるもの (プロジェクトを書き出した記録とモデルの定義の置き場の記録があり, 記録のプロジェクトが今もある). 他 (書き出していない, 書き出してあるが定義の置き場の記録が無い, 読めない, 問題の設定のファイルでない, プロジェクトを移したか消した) は理由を付けて並べ, 選べなくする. 記録の無い理由はプロジェクトの場所の記録 (`project.path`) の有無で分ける (書き出したプロジェクトを「書き出していません」と出さないため. 定義の置き場の記録が無いものは, プロジェクトのディレクトリを選ぶと保存できることを添える). 置き場が無ければ, 置き場の場所と下の欄で選べることを出す
    - 「データセットから入力と出力を作る」: データセットのディレクトリの場所を書き (前に読んだ場所が入る. 下の欄でプロジェクトの保存先を確かめると, この欄に打つ前ならその記録のデータセットの場所 (記録の無いプロジェクトは骨組みの config の `data.dataset` をプロジェクトのディレクトリから求めた場所. 学習のスクリプトが読む場所と同じにするため) が入る), 押すとバックエンドが ML-EDA の `model_inputs` で読む. 結果は本体の定義に 1 回の変更として入れる (元に戻すで戻せる. 部分モデルを編集している間は理由を出して選べない)
        - 入力: データセットの入力の名前, 形, 型にする. 形のバッチの次元 (`null`) は例の大きさ 4 にする (形の推定の例にだけ使うため). 他の決まらない次元 (大きさの混ざる画像の高さと幅など) は, 定義の入力が同じ次元の数の形を持てばその値のまま, 無ければ 4 にする (同梱の例の 4 の倍数の大きさを壊さないため). API は例の形 (`shape`) とデータセットの形 (`dataset_shape`. 決まらない次元は `null`) の両方を返す. 定義の入力とデータセットの入力が 1 つずつで名前が違えば, 名前を変えてつなぎ先も書き換える. 同じ名前の入力は形と型だけを変え, 値の作り方と位置は残す. データセットに無い入力は, つないでいなければ消し, つないでいれば残して知らせる. データセットの入力と同じ名前のノードがある場合は, 何も変えずに知らせる (つなぎ先が入力を指すように変わるため)
        - 入力に直につながる, `in_features` の引数を持つノード (`nn.Linear` など) は, `in_features` を入力の最後の次元にする. `in_channels` の引数を持つノード (`nn.Conv2d` など) は, 3 次元以上の入力の 2 番目の次元 (チャンネル) にする. `num_embeddings` の引数を持つノード (`nn.Embedding`) は, 文の語の番号の入力なら語彙の大きさ (ML-EDA の `model_inputs` の入力の `vocabulary`. API も同じ名前で返す) にする (語彙より小さい埋め込みは学習の途中で番号が表の外になって止まるため)
        - 出力の大きさ (`outputs`. 分類はクラスの数, 回帰は 1, 予測は先の期の数か 1. 画像と領域は背景を含む領域のクラスの数, 点群は出す点の数): 部品の無い定義で入力が 2 次元なら, `nn.Linear` の `head` を置いて出力 `out` につなぐ. 出力が 1 つで, そのつなぎ元のノードが `out_features` か `out_channels` (画素ごとのクラスのスコアを出す畳み込み. 同梱の例 `unet_segmentation` の `head`) の引数を持てば, それを出す値の数にする. つなぎ元が `op.Reshape` で, その 1 つ前のノードが `out_features` を持てば, `shape` の最初の次元を出す値の数にし, 前の `out_features` を `shape` の全ての次元の積にする (点の数 × 3 を出して並べ直す形. 同梱の例 `point_cloud_predictor` の `decode2` と `cloud`). それ以外 (出力が複数, 最後がこれらを持たない部品, タスクを決めていない) は変えずに, 手で入れる値を知らせる
        - 入れた結果 (入力の形 (データセットで決まらない次元は `?`), タスク, 目的の列か正解の項目と種類, クラスの数, 出す値の数, 変えたノードと残したもの) は, 欄の下と部品の一覧の上に知らせる
    - 「プロジェクトに保存」: 学習のプロジェクトのディレクトリか, 問題の設定のファイル (`problem.yaml` か, ML-Pathfinder の置き場の問題の設定) の場所を書き, 「保存先を確かめる」で保存先を出してから保存する. 保存先は次の順に決める
        - 問題の設定のファイルか, プロジェクトの中の `problem.yaml`: ML-Quest の `handoff` の `model.project_model_spec` (ML-Quest が骨組みを書き出したときの記録). 記録のプロジェクトの場所 (`project.path`) が学習のプロジェクト (`configs/default/train.yaml` を持つ) で, その中の場合だけ書く (手で書いた記録や, 移したか消したプロジェクトの記録で, よその YAML を書き換えないため)
        - 記録の無いプロジェクト (`configs/default/train.yaml` を持つディレクトリ): config の `model.spec` (書いていなければ骨組みの既定の `models/model.yaml`. 学習のスクリプトが読む場所に書くため. リンクをたどった先もプロジェクトの中に限る)
        - プロジェクトの中の `problem.yaml` を読めない場合 (ML-Quest が無い, 知らない版, 直すところがある) は, 既定の場所に替えずに理由を出して止まる (記録と違う場所に黙って書かないため)
        - 保存先が学習の設定のディレクトリ (プロジェクトの `configs/` の中. `configs/default/train.yaml` も) なら, 理由を出して書かない (config の `model.spec` の書き間違いで, 学習の設定を消さないため. 大文字と小文字は区別しない)
        - 保存先がプロジェクトの直下の `problem.yaml` か, `data/` か `outputs/` の中なら, 理由を出して書かない (ML-Quest が書き出した問題の設定の写しと写したデータ, ML-EDA が書き出したデータセット (`outputs/dataset`) と ML-Found の実験のディレクトリ (`outputs/`) を, モデルの定義で上書きしないため. 大文字と小文字は区別しない). `outputs/` は ML-Found の既定の出力先の名前で, config の `experiment.output_dir` で変えたプロジェクトでも既定の名前で判定する
        - 保存先までの途中の名前がディレクトリでない (ファイルなど) なら, 理由を出して書かない (確かめが通った後に, 保存でディレクトリを作れずに失敗しないため)
        - 保存先の拡張子が小文字の `.yaml` か `.yml` でない (`A.YAML`, `a.Yml` など) なら, 理由を出して書かない (ML-Dashboard の「モデルの定義の候補」は小文字の拡張子のファイルだけを並べるため). 大文字と小文字を区別しないファイルシステムで, 名前の保存先が大文字の拡張子の既にあるファイルになる場合も同じで, ファイルの名前を直すように出す
        - 「models/ の下の名前」を書くと, 上で決めたプロジェクトの `models/<名前>.yaml` に保存する (空なら上の既定の保存先). モデルの候補を並べるため (ML-Dashboard の学習の起動の「モデルの定義の候補」は, プロジェクトの `models/` の下の YAML を一覧にする). 名前は置き場の名前と同じ規則 (英数字, `_`, `-`. 先頭に `-` は使えない. 64 文字まで) に限り, 中のディレクトリは作らない (`/` を受け取らないことで, `models/` の外と `..` を断つため). `models/` かそのファイルがリンクなら, 理由を出して書かない. 問題の設定の記録の保存先がプロジェクトの外なら, 名前を書いても理由を出して書かない (記録を信じられないため)
            - 同じ名前の `<名前>.yml` が既にあり `<名前>.yaml` が無ければ, `.yml` の方を保存先にして上書きを確かめる (ML-Dashboard の候補に同じ名前を 2 つ並べないため). 大文字と小文字だけ違うファイルを同じファイルとして扱うファイルシステムでは, 保存先と確かめの文に実際のファイル名を出す
            - 名前の保存先が既定の保存先と同じファイルなら, 既定の定義を上書きすることを添える. どちらもまだ無い場合は場所の文字で比べ, 大文字と小文字だけ違う場合は, 置き場が大文字と小文字を区別しないとき (一番近いある上のディレクトリの名前を, 大文字と小文字を入れ替えて探して見分ける. 見分けられる名前が無ければ区別しない扱い) だけ同じファイルとみなす (書くと既定の定義と同じファイルになるため). 確かめた後に場所か名前を書き換えたら, 確かめ直すように出す. 確かめに失敗した場合 (名前が規則に合わない, 書けない保存先など) は誤りだけを出し, 前に確かめた保存先, 一覧の問題の設定の選択も消す (書き換えたように読めて迷わせないためと, 失敗した場所に前の保存先のまま書かないため). 確かめが重なった場合 (確かめの間に一覧から選んだ場合) は, 最後に送った確かめの結果だけを出す (遅れて返った前の結果で, 後の結果を上書きしないため)
        - config の `model.spec` は書き換えない. ML-Dashboard が候補ごとに書き換えて学習するためで, 既定の定義はプロジェクトの `configs/default/train.yaml` の `model.spec` のまま
        - 保存先までの無いディレクトリ (`models/a/` など何段でも) は, プロジェクトの直下から順に作る. プロジェクトのディレクトリそのものと, その外には作らない (移したか消したプロジェクトの場所を作り直さないため)
        - 既にファイルがある場合は, 上書きしてよいかを確かめてから書く. 保存の要求には確かめた保存先を添え, 書くときに決め直した保存先と違えば書かない (上書きの許しを確かめた保存先にだけ効かせるため. 確かめた後に同じ名前の `.yaml` が作られた場合や, config の `model.spec` が変わった場合). 保存が断られた場合 (保存先が変わったか, 確かめた後に他でファイルが作られた) は, 保存先を確かめ直して理由を出し, 見直してから押し直すようにする (確かめていない保存先と, 既にあると知らせていないファイルに書かないため). 保存するのは定義全体 (置き場への保存と同じく `dump_spec` が書ける最も低い版). 置き場の定義とは別のファイルなので, 置き場の保存していない変更の印 (`*`) は変えない. 保存すると欄の下と画面の右下に「<保存先> に保存しました」と出す
        - 最後に確かめたプロジェクトの場所とデータセットの場所は, ブラウザ (`localStorage`) に覚えて次の欄に入れる. `models/` の下の名前は覚えない (候補ごとに変える名前なので, 前の名前のまま保存して別の候補を上書きしないため)
- **自作の部品 (起動の設定のモジュール)**: 研究の自作の部品は, バックエンドを起動する環境の `ML_CREATEARCHITECTURE_MODULES` (モジュールの名前をカンマで区切って並べる. 例: `my_lab.units,my_lab.blocks`) に書いたモジュールだけを, 起動のときに ML-ModelControl の `register_units_from` で読み込む (宣言の書き方は ML-ModelControl の docs/DESIGN.md の「自作の部品のモジュール」). このリポジトリの他の起動の設定 (`ML_CREATEARCHITECTURE_HOME`, `ML_CREATEARCHITECTURE_TOKEN`, `ML_MODELCONTROL_WEIGHTS_DIRS`) と同じく環境変数にし, 設定のファイルは作らない
    - 起動のログに, モジュールごとに読み込んだ部品の名前を出す (「自作の部品を読み込みました: my_lab.units → my.Block, my.Pair」). 読み込めないモジュールがあれば, 理由を出して起動を止める (書き間違いに気付かないまま, 定義が「登録されていない」誤りになるのを避けるため)
    - 部品の一覧では, 自作の部品をモジュールごとに「自作 (my_lab.units)」のまとまりにし, 組み込みの部品の後に置き, 開いた状態で始める (Python のコードから直に登録した部品は「自作」)
    - 登録されていない部品を使う定義 (自作の部品の定義を, そのモジュールを書かずに起動したアプリで開いた場合など) では, そのノードの誤り (ML-ModelControl の `unknown_unit`) の下と, 何も選んでいない場合の全体の情報に, 部品を宣言したモジュールの名前を起動の設定 `ML_CREATEARCHITECTURE_MODULES` に足して起動し直す案内, 起動の例, 今読み込んでいるモジュールの一覧 (`GET /api/modules`) を出す. 定義に書いた名前からは何も読み込まない. 画面の型を作るための仕様の書き出し (`--openapi`) ではモジュールを読み込まない
    - 画面, API, 定義のファイルからはモジュールを選べない (起動する人だけが選ぶ). 書いたモジュールは起動のときに任意のコードとして動くので, 信頼できるコード (自分や仲間が書いたもの) だけを書く
- **左右の欄**: 部品の一覧と詳細は, キャンバスの左上と右上のボタンで畳める. 幅 1200 px 未満の画面では畳んで始める. `/` で部品を探すと左の欄を開き, キーボードで部品を置くと詳細を開いて引数の最初の欄 (無ければ入力のつなぎ先) に移る
- 編集するたびに (少し待ってから) バックエンドで確認と形の推定をし, 結果をノードに重ねる
- キャンバスの線は定義の各ノードの `inputs` と 1 対 1 に変換する (可変の数の口は, 線を引いた順がリストの順)
- **元に戻す・やり直す** (Delete キーで消した線とノードは 1 回分. やり直しは Ctrl+Shift+Z か Ctrl+Y, Mac は Cmd): 定義を履歴付きの値で持つ (上限 100 回). 同じノードのドラッグの続けての移動は 1 回分にまとめ, 中身の同じ変更は残さない. 定義を開くか新規にすると履歴を消す. Ctrl+Z (Mac は Cmd+Z) と Ctrl+Shift+Z (か Ctrl+Y), 文字を打つ欄の中では, 打ちかけの文字がある間はブラウザの標準の取り消し, 値を反映した後 (打ちかけの文字が無い間) は定義を戻して欄にも出す
- **下書き**: 保存していない変更は, 少し待ってからブラウザ (`localStorage`) に画面 (タブ) ごとの下書きとして残す (書けない場合は古い下書きを残さないように消す). 次に開いたとき, その画面の下書き (無ければ他の画面の一番新しいもの. 14 日より古いものは出さない) を「保存していない定義の下書きがあります」と出し, 「下書きを開く」か「下書きを捨てる」を選べる (開くと保存していない変更として開く. 今の変更がある場合は確かめる). 保存する名前の欄に打った, まだ保存していない名前も下書きに残し, 開くと欄に戻す (下書きは定義の変更を守るためのもので, 名前だけを変えた場合は残さない. 新規, 開く, 保存で打った名前を消す. 保存の間は下書きを開く・捨てるを止める). 聞いている間は前の下書きを上書きしない. 保存, 新規, 開く, 捨てる, 保存した時点と同じに戻した場合に, その画面の下書きを消す
- **使えない部品の口**: ライブラリが無い部品と登録されていない部品のノードは, 定義のつなぎ先から口を推し量って (入力の口は inputs の名前, 出力の口は他から「ノード:口」で参照される名前) 線を描く (同梱の例をライブラリを入れずに開いても, つながりが見えるように)
- **置き場所と整列**: 新しく置くものは, 見えている範囲の真ん中の近くで他のノードと重ならない所に置く. 入力かノードを選んで部品を置くと, その右に置き (見えている範囲の外になる場合は, その位置に置いて表示を動かす), 置いた部品に必須の口か可変の数の口があれば, つなぎ元の最初の出力の口から最初の必須の口へ線を引く (出力が複数の部品も, 最初の口が主な出力 (`nn.MultiheadAttention` の `output`, `nn.LSTM` の `output` など). 参照は `ノード:口` になるので, 違えば詳細で選び直す. 出力が複数の部品から引かないと, 自己注意の後に置いた `op.Add` に注意の出力がつながらないまま誤り 0 件になるため). 他の口は, 同じ名前のモデルの入力 (GNN の `edge_index` など) があればそれにつなぐ. 出力を加えたとき, どこにもつながっていないノードが 1 つだけで出力の口が 1 つならそれにつなぐ. 置いた部品が選ばれるので, 続けて置くと一直線につながる (枝分かれさせる場合は, つなぎ元を選び直す). ノードの幅は整列の段の間隔に収まる上限 (236) までにし, 長い口の名前と形は省略してマウスを重ねると全体を出す. 整列 (後に全体が見えるように表示を合わせる) はつながりの深さで左から右へ段に分け (入力は最初, 出力は最後の段), 段が多い場合は折り返して下の行に続ける. 位置 (`ui`) の無い定義を開いた場合は, 位置の無いものにだけ同じ並べ方で位置を書く
- **読み上げと focus**: 先頭に「キャンバスへ移る」のリンク. ノードと線に日本語の読み上げの名前 (「ノード relu1 (nn.ReLU), 出力 out [4, 16]」「x から relu1 の input への線」). 明るさの切り替えは押した状態 (`aria-pressed`) を持つ. 詳細の欄の Esc は選んでいるノード (無ければキャンバス) に戻り, 消した後と Ctrl+S の後も focus を失わない. 全体のパラメータ数はマウスを重ねると正確な数
- **キーボード**: Ctrl+S (Mac は Cmd+S) で保存する (文字を打つ欄の中でも, 打ちかけの値を反映してから). Esc で編集している部分モデルから 1 つ上に戻る (押し続けても 1 つずつ). `/` で部品を探す欄に移る (Esc と `/` は文字を打つ欄の中では効かない)
- **複製と写し**: 選んだ部品のノードを引数ごと複製し (Ctrl+D), 写して貼れる (Ctrl+C, Ctrl+V. アプリの中だけ). つなぎ先は写さない

### 部分モデル

- **写す**: 部品の一覧の「別の定義を部品にする」で, 保存した定義か同梱の例を今の定義の `subgraphs` に写し (ML-ModelControl の部分モデル), 一覧の「部分モデル」から `sub.<名前>` の部品として置く. 写した定義の入力が入力の口, 出力が出力の口になる. 参照ではなく写すので, 元の定義を後で変えても変わらない. 今開いている定義自身は選べない. 誤りのある定義を写す場合は, 誤りの数と最初の誤りを出して写すかを確かめる (確認だけで形は推定しない). 写した結果 (付け直した名前など) と消した結果は一覧の上に知らせる
- **名前**: 写した定義の名前. 同じ名前で中身の同じものは 1 つにまとめ, 中身の違うもの, Python の予約語, 書き出すコードのクラスの名前 (本体の `Model` と他の部分モデル) と重なるものは番号などを付けた名前にする (写す定義の中の部分モデルも同じく付け直し, 中の `sub.<名前>` も直す). 中身の比較では写した元を除く (写した元だけが違う同じ中身は 1 つにまとめる)
- **写し直す**: 写した元 (保存した定義か例の名前) を部分モデルの `ui.source` に書き, 一覧の写し直しのボタンで, 同じ名前のまま元の定義の今の中身に置き換える (元の定義を直した後に. 元に戻すで戻せる). 口が変わった場合は本体の誤りになる. 前の中身の位置は同じ名前のものに残し, 位置だけの違いは変わっていない扱い. 前の中身だけが使っていて使われなくなった部分モデルは消す. 写す定義の中に同じ名前の部分モデルがあれば番号を付けた名前にして, 自分を使う形にしない. 読み込みの間に定義が変わった場合は, その時点の定義に対して行い, 部分モデルが無くなっていれば何もしない. 今開いている定義自身からは写し直さない
- **消す**: 使っているノードの無い部分モデルは一覧から消せる (他の部分モデルの中で使っている場合は, そちらを先に消すように知らせる)
- **中身を読む**: 選んだ部分モデルのノードの詳細で, 中身 (入力の元の形, 中のノードの部品と引数, 出力) を読める. 部分モデルの中の誤りは, 定義全体の誤りとして場所 (`subgraphs.<名前>...`) 付きで出す
- **中身を編集する**: 部分モデルを使うノードの詳細の「部分モデルの中身を編集」かノードのダブルクリックで, その部分モデルを 1 つの定義としてキャンバスで編集する. キャンバスの上に階層 (本体 › sub.outer › sub.block. 入れ子で開ける) と, 使っているノードの数を出し, 階層の名前で戻る. 変更は定義の中の部分モデルに書き戻し, 元に戻すの履歴は本体と同じ (戻して部分モデルが無くなった場合は, あるところまで戻る). 置くと循環になる部品 (自分自身と, 中で自分を使う部分モデル) は一覧に出さず, 貼り付けもしない. 位置の無い部分モデルは編集を始めるときに位置を書く (履歴に残さず, 保存していない変更にもしない). 保存, Python の書き出し, 別の定義を部品にする, 部分モデルを消す操作は定義全体に対して行い, YAML の表示は編集している部分モデルの中身を出す
- **編集している間の確認**: 確認と形の推定はその部分モデルだけで行う (自分自身を除き, 中で使う部分モデルだけを持たせる). 本体の部分モデルを開いた場合は, 本体も形の推定をして, その部分モデルを使うノードを計算の順に見て, 全ての入力の口の形が分かる最初のノードに入る形を入力の形にして推定する (入力から来る値は入力の型と値の作り方, ノードから来る値は出力の型と 0. 保存する入力の形は変えない. 「形はノード x に入る形で推定」と出す). そのようなノードが無い場合と入れ子で開いた場合 (本体は確認だけ) は, 部分モデルの入力に書いた形で推定する. 本体の誤り (口の名前を変えて本体のつなぎ先が合わなくなった場合など) も確かめて「本体に誤り n 件」と出す
- **ノードだけの部分モデル**: 部分モデルを使うノードの詳細の「このノードだけの部分モデルにする」で, その部分モデルを写して `<元の名前>_<ノード>` の部分モデルにし (2 つ以上のノードが使う部分モデルだけ), そのノードだけが使うようにする (同じ部分モデルを重ねた中の 1 段だけチャンネル数を変える場合など). 写したものは写し直しの対象にしない

## 4. API

| 経路 | 内容 |
| --- | --- |
| `GET /api/units` | 部品の一覧 (ML-ModelControl の `describe_units`. 起動の設定のモジュールから読み込んだ自作の部品は `module` にモジュールの名前) |
| `GET /api/modules` | 起動の設定 (`ML_CREATEARCHITECTURE_MODULES`) で読み込んだモジュールと, モジュールごとの部品の名前と, 設定の環境変数の名前 (登録されていない部品の案内に使う) |
| `POST /api/check` | 定義を確かめ, 誤りと注意, ノードごとの形とパラメータ数, 保存する形の YAML を返す (`validate` と `infer`. 形の推定をせずに確かめるだけにもできる) |
| `GET /api/examples`, `GET /api/examples/{name}` | ML-ModelControl に同梱した例のモデルの一覧と読み込み (「開く」から例を選んで編集を始める) |
| `GET /api/models` | 置き場の定義のファイルの一覧 |
| `GET /api/models/{name}` | 定義を読み込む |
| `PUT /api/models/{name}` | 定義を保存する |
| `DELETE /api/models/{name}` | 保存した定義を消す (名前が規則に合わない場合は 400, 無い場合は 404, 消せない場合は 500) |
| `POST /api/pretrained` | ノードの部品の名前と引数の値から, 学習済みの重みのライセンスの情報を返す (ML-ModelControl の `pretrained_info`. 重みを読まない場合は `null`, 登録簿に無い部品は 404). 配布元を読むのでネットワークを使う |
| `POST /api/weights` | 定義を組み立てて外部の重み (ノードの `weights`) を読み, ノードごとの報告 (読めた / 形の違う / 新しい / 使わない重みの数とキーの一部, 出どころ, ライセンス) を返す (ML-ModelControl の `build_model` と `weights_report`). 相対のパスは定義の置き場から. 読めるのは, リンクをたどった先が定義の置き場か, バックエンドを起動する環境の `ML_MODELCONTROL_WEIGHTS_DIRS` (パスの区切りで並べる) のディレクトリの中にあるファイルだけで, 大きさの上限は既定 4 GiB (`ML_MODELCONTROL_WEIGHTS_MAX_BYTES`). 読むのは `torch.load` の `weights_only=True` と safetensors (読めるキーだけ) で, コードは動かさない. 誤りの文に手元の絶対のパスは出さない. 確認と同じ見積もり (入力の例の要素数とパラメータ数の上限) を超えるモデルは組み立てない. 外部の重みの無い定義は組み立てずに空の報告. 読み込みは 1 つずつ (途中なら待たずに知らせる). 読めない場合は `ok` が偽で誤りの文. ファイルとネットワークを使う |
| `POST /api/export` | 同じ計算をする Python のコードを書き出す (ML-ModelControl の `export_python`) |
| `POST /api/dataset/inputs` | データセットのディレクトリから, 入力 (名前, 形, 型. 形はバッチの次元を例の大きさにしたものと, 決まらない次元が `null` のデータセットの形), タスク, 目的の列, クラス, 正解の種類, 出す値の数を返す (ML-EDA の `model_inputs`. ML-EDA が無い場合は 501, 場所が無い場合は 404, 読めない場合は 422) |
| `GET /api/problems` | ML-Pathfinder の置き場の問題の設定の一覧 (置き場の場所と, 更新の新しい順の 1 件ずつの場所, 名前, 作った時刻, 更新時刻, 使えるか, 使えない理由, プロジェクト, データセット, 保存先). 置き場が無ければ空, 読めなければ理由. ML-Quest が無い場合は 501 |
| `POST /api/project/target` | プロジェクトのディレクトリか問題の設定のファイル (と `models/` の下の名前 `name`. 無いか空なら既定) から, モデルの定義の保存先, プロジェクトとデータセットの場所, 既にあるか, 名前の保存先が既定の保存先と同じファイルか (`default`) を返す (上の「3. 画面」の「データセットとプロジェクト」. 問題の設定は ML-Quest で読む). 保存先に書けない場合は理由を付けて 422 (保存先を決められない, YAML のファイルでない, 拡張子が小文字でない, `configs/` の中, 直下の `problem.yaml`, `data/` か `outputs/` の中, 途中の名前がディレクトリでない (ファイルか壊れたリンク), ファイルでないものがある) |
| `PUT /api/project/model` | 定義をプロジェクトの保存先 (`name` は上と同じ) に書く. 確かめた保存先 (`target`. 上の `path`) を送ると, 決め直した保存先と違えば `overwrite` に関わらず 409. 既にある場合は `overwrite` が真の時だけ書き, 偽なら 409. 定義として読めない場合と, 保存先が `configs/` の中, 直下の `problem.yaml`, `data/` か `outputs/` の中, 途中の名前がディレクトリでない場合は 422 (保存先の確かめも同じ), 書けない場合は 500. 書いたファイルの権限は普通のファイルと同じ (起動のときの umask に従う) |
| `POST /api/project/experiments` | プロジェクトのディレクトリか問題の設定のファイルから, プロジェクト, 探した実験の置き場, 探さない置き場と打ち切りの理由 (`notes`), 新しい順の実験 (置き場からの `run`, 置き場 `root`, 場所, 写した元の定義の場所, 保存する名前の候補, `run.json` の状態, 時刻, 開けるか, 開けない理由) を返す. 場所が無い場合は 404, 学習のプロジェクトでない場合は 422 |
| `POST /api/project/experiment-spec` | 一覧の実験 (`run` と置き場 `root`) の定義の写しを読み, 保存する名前の候補と定義を返す. 置き場の 3 段を, 子のディレクトリの名前と `run` の名前を比べて辿り (送られた文字から場所を組み立てない), 無ければ 404, `root` を送らずに複数の置き場で `run` が重なれば 409, 開けないか, 別名や深い入れ子を含むか, 定義として読めない場合は 422 |

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| 部品 | モデルの 1 つの単位 (層, 演算, 外部のライブラリのモデルなど). ML-ModelControl の登録簿にあるもの |
| ノード | キャンバスに置いた部品の 1 つ. 名前, 引数の値, 入力のつなぎ先を持つ |
| 口 | ノードの入る口と出る口. 線は出る口から入る口へ引く |
| 定義 | モデルの入力, ノード, 出力をまとめたもの (ML-ModelControl の定義の形. YAML か JSON) |
| 部分モデル | 別の定義を, この定義の中で 1 つの部品 (`sub.<名前>`) として使うもの (定義の `subgraphs`) |
| 形の推定 | 入力の形から, 各ノードの出力の形とパラメータ数を求めること |

## 6. 置き場

既定は `~/.ml-createarchitecture/` (環境変数 `ML_CREATEARCHITECTURE_HOME` で変えられる).

- `models/<名前>.yaml`: 保存した定義. 名前はファイル名の規則 (英数字, `_`, `-`) に限り, 置き場の外には書かない
- 置き場の外に書くのは「プロジェクトに保存」の保存先だけ (下の「7. 安全」)
- 保存していない変更の下書きは置き場に置かず, ブラウザ (`localStorage`) に残す (上の「3. 画面」の「下書き」)

## 7. 安全

既定では `127.0.0.1` だけで待ち受ける (他のホストを指定すると警告を出す). 起動ごとのトークン (Cookie かヘッダー) を持つ要求だけを API で受け付け, 他のサイトからの書き込み (Origin が接続先と違うもの) と別のホスト名での接続を断る. 手元のファイルを読めるので, トークンは他の人に渡さない.

- 他のサイトから Hugging Face のモデルの取得などを起こされないように, 画面からの要求も全てトークンを確かめる
- 定義の名前はファイル名の規則に限り, 置き場の外には書かない. 外部の重みを読むのは定義の置き場と `ML_MODELCONTROL_WEIGHTS_DIRS` の中だけ (上の「4. API」の `POST /api/weights`)
- 自作の部品のモジュールは起動する人だけが選ぶ (上の「3. 画面」の「自作の部品 (起動の設定のモジュール)」)
- 「プロジェクトに保存」で書くのは, 拡張子が小文字の `.yaml` か `.yml` の保存先 1 つだけ. 名前で選ぶ保存先はプロジェクトの `models/` の直下に限り, リンクには書かない. config (`model.spec`) は書き換えない. 問題の設定の記録の保存先はプロジェクトの場所の中に限り, 学習の設定 (`configs/` の中), 問題の設定の写し (直下の `problem.yaml`), データと実験 (`data/` と `outputs/` の中) には書かず, 作るディレクトリもプロジェクトの中だけ. 既にあるファイルは確かめてから上書きし, 上書きの許しは確かめた保存先にだけ効かせる. 書く前に定義として読めることを確かめ, 一時ファイルに書いてから置き換える. 場所は絶対のパス (`~` から書ける) だけを受け取る
- 実験の定義の写しを読むのは, プロジェクトの中で途中にリンクの無い実験の置き場の, 一覧に出す実験の `model_spec.yaml` (リンクでない普通のファイル, 16 MiB まで) だけ. 読むだけで, 実験のディレクトリには書かない

## 8. 課題の型への広げ方

部品と定義の形は ML-ModelControl に足し, この画面はそれを使う (受け持ちごとの雛形は「開く」の同梱の例, 定義の版 2 は「パラメータの状態」, 学習済みの重みは「学習済みの重みのライセンス」, 研究の自作の部品は「自作の部品 (起動の設定のモジュール)」).
