# 設計

ML-CreateArchitecture の今の設計と決まりをまとめる. まだやっていないことは [TODO.md](../TODO.md) に置く.

## 1. 役割と位置づけ

ML-ModelControl の部品を GUI で並べてつなぎ, モデルを組み立てるローカルの Web アプリ. 「機械学習を全て GUI 上で行う」アプリ (問題の設定, データの分析, モデルの作成・選定, モデルの学習・評価, 推論の段階に分けて作る) のうち, 「モデルの作成・選定」の段階の画面.
コードを書かずに, 部品の一覧から選んで置き, 線でつなぎ, 引数をフォームで決め, 形とパラメータ数を確かめながらモデルの定義を作る.

| 部分 | 中身 |
| --- | --- |
| バックエンド | Python, FastAPI. ML-ModelControl を呼ぶ API と, 定義のファイルの一覧, 読み込み, 保存. データセットから入力と出力を読む API と, プロジェクトに保存する API (ML-EDA と ML-Quest を通す) |
| 画面 | TypeScript, React, Vite. グラフの編集に React Flow (`@xyflow/react`) を使う |

ML-Dashboard と同じ構成と道具 (uv, pnpm, Ruff, mypy, Prettier, oxlint, OpenAPI から画面の型を作る) にそろえ, 将来の統合を楽にする.

### 役割

構想 (全体で 1 つのアプリ) の中で「モデルの作成・選定」の段階を受け持つ.

- 前の段階から受け取るもの: 問題の設定 (ML-Pathfinder の置き場の `problem.yaml`. ML-Quest で読む. 受け持ちに合う雛形と, 骨組みの入力と出力の約束), データの分析の段階が作ったデータセットの説明 (`dataset.yaml`. ML-EDA で読む. 入力と出力の形)
- 後の段階へ渡すもの: モデルの定義 (ML-ModelControl の YAML. プロジェクトの `models/` の下に書く). 学習の段階 (ML-Dashboard が動かす ML-Found の学習) が読む

### 要件

| 要件 | 今できていること | 足りないこと |
| --- | --- | --- |
| 部品を並べ, つなぎ, 引数を決めて定義を作り, 形とパラメータ数を確かめる | 画面の部品の一覧, キャンバス, 詳細, `POST /api/check` と `POST /api/export`. 保存と読み込みは `/api/models` | 統合以外は無し |
| データセットから入力と出力を決める | `POST /api/dataset/inputs` (ML-EDA と ML-Quest を通す). 場所は画面のダイアログに利用者が入れるか, 殻で選んだ問題の設定の記録から入る (「3. 画面」の「殻で選んだ問題の設定」) | 統合以外は無し |
| 問題の設定の受け持ちに合う雛形と既製のモデルから始める | `GET /api/problems`, `GET /api/examples`, `POST /api/templates/match` と `adapt`. 問題の設定の一覧は ML-Pathfinder の置き場から読む | 統合以外は無し (まだ扱っていない型の雛形は低) |
| 定義をプロジェクトに保存し, 学習の段階へ渡す | `PUT /api/project/model`. 骨組みの入力と出力に合うかを確かめて書く. 学習の実験の定義の写しも開ける (`/api/project/experiments`) | 保存した後に学習の段階へ移る導線 (殻の段階の並び. 統合) |
| 置き場, トークン, 待ち受けを外から決められる | `create_app(data_dir, token, allowed_hosts, modules)` と環境変数 `ML_CREATEARCHITECTURE_HOME`, `ML_CREATEARCHITECTURE_TOKEN`. ポートは `--port` (起動のコマンドだけ). 確かめを持たない API だけのアプリ (`create_api`) を殻の頭の下に mount できる (「4. API」). 画面の根の部品 (`StageApp`) に API の頭と殻で選んだ問題の設定を渡して載せられる (「3. 画面」の「根の部品」) | 下の「統合に向けて足りないこと」 |

### 統合に向けて足りないこと

殻 (ML-Studio) は 5 つのアプリを submodule で持ち, 1 つのコマンドで 1 つのポートを開く. 起動ごとのトークンと Origin の確かめは殻が 1 つだけ持つ. 各アプリは自分のバックエンドを `/api/<段階>`, 画面を `/<段階>` の下に載せられる形にし, 単独でも今まで通り動く.

- 共通の部品と言葉: 見出し, 段階の並び, 誤りの出し方は各アプリの画面が別々に持つ. 殻の段階の並びと共通の部品にそろえ, 段階の名前と画面の言葉を 5 つのアプリでそろえる

## 2. 使うライブラリと約束

ライブラリは ML-ModelControl (submodule. ML-Dashboard と ML-Found の関係と同じ). ML-EDA と ML-Quest は追加の依存 `project` にし (「データセットとプロジェクト」のダイアログだけで使うため), `make setup` の既定で入れる. 2 つは git の依存で持ち, `backend/uv.lock` の版を殻 (ML-Studio) の設計の「共通のライブラリの版」の表の版にそろえる (殻の 1 つの環境には 1 つの版しか入らず, 表の版でこのアプリのテストを通しておくため. 上げるときは `uv lock --upgrade-package ml-eda --upgrade-package ml-quest` で表の版になったことを確かめる). ML-ModelControl はまだ表に無いので submodule の版のまま. 入れていない場合は, その操作で入れ方 (「make setup (EXTRAS を書く場合は project も含める)」) を出す.

- **他の段階のファイルは, その約束を持つライブラリを通して読む**: データセットの説明 (`dataset.yaml`) は ML-EDA, 問題の設定は ML-Quest を通して読み, このアプリは自分では開かない. ML-Inference がデータセットを ML-EDA で読むのと同じ理由で, 版の確かめと読み方を持ち主の 1 か所にまとめ, 約束の版が上がっても読む側を直さずに済むようにするため (知らない版は持ち主の誤りの文で止まる)

- モデルの定義 (YAML か JSON) の読み書き, 確認, 形の推定, 組み立てと, 雛形をデータの幅に合わせる書き換え (`adapt_example`) は全て ML-ModelControl が行う. このアプリは画面と, 定義のファイルの置き場だけを受け持つ
- 定義のファイルの形は決めない. 読み書きするのは ML-ModelControl の定義の形だけで, その形が他の段階 (学習など) との約束になる
- 読み書きするファイル:

| ファイル | 読むか書くか | 約束 |
| --- | --- | --- |
| モデルの定義 (`models/<名前>.yaml`) | 読み書き | ML-ModelControl の定義の形. 版 1 から版 3 を読み, 保存は `dump_spec` が書ける最も低い版で書く (下の「3. 画面」の「パラメータの状態」と「引数に書く部品」) |
| 外部の重み (`torch.load` で読めるファイル, safetensors, Hugging Face) | 読むだけ | ML-ModelControl の `build_model` と `weights_report` (下の「4. API」の `POST /api/weights`) |
| 書き出す Python のコード | 書く (コピーかダウンロード) | ML-ModelControl の `export_python`. ML-ModelControl を入れていない環境でも動く |
| データセットの説明 (`dataset.yaml`) | 読むだけ | ML-EDA の約束. `ml_eda.model_inputs` で入力の名前, 形, 型と, タスク, 目的の列, クラス, 正解の種類, 出す値の数を読む (版 1 の列の正解と, 版 2 と 3 のファイルの組 (画像と領域, 撮影か点群と点群). 知らない版と知らない項目の組は ML-EDA の誤りの文を出す) |
| 問題の設定 (ML-Quest の YAML) | 読むだけ | ML-Quest の約束. `load_problem` と `handoff` で, プロジェクトの記録 (`model.project_model_spec`, `project.path`, `data.project_dataset`) と, 受け持ちに合う雛形 (`model.example`. ML-ModelControl の同梱の例の名前. 一から学習する受け持ちだけで, 無ければ `None`) を読む. 表の生成の問題の設定では, `table_encoding` で, データセットの符号化した行の幅 (学習のスクリプトが学ぶ行の幅) を読む. モデルの定義を保存する前に, `model_contract` と `check_model_contract` で, 骨組みの学習のスクリプトが読む入力と出力の約束と比べる (下の「3. 画面」の「プロジェクトに保存」). 並べるの問題の設定では, `rank_encoding` で, 反応の表の学習用の利用者と品物の数 (学習のスクリプトの 2 塔の入力の大きさ) を読み, `project_of` の `path` のプロジェクトの `configs/default/train.yaml` の `data.valid` と `data.test` (数で書いてあれば) を分ける割合として渡す. ML-Pathfinder の置き場 (`ML_PATHFINDER_HOME`. 無ければ `~/.ml-pathfinder`) の `problems/<識別子>/problem.yaml` を一覧にする (ML-Fathom の一覧と同じ置き場と読み方) |
| プロジェクトのモデルの定義 (骨組みでは `<プロジェクト>/models/model.yaml`) | 書く | ML-ModelControl の定義の形 (置き場の定義と同じ書き方). 学習のスクリプトが config の `model.spec` から読む |
| 学習の実験の定義の写し (`<実験の置き場>/<名前>/<日付>/<時刻>/model_spec.yaml`) | 読むだけ | ML-Found の実験のディレクトリの形 (ML-Found の `docs/FORMAT.md`). `source.yaml` の `model_spec` の `status` と `sha256` で, 学習を始めたときの定義かを見分ける (下の「3. 画面」の「実験の定義の写しを開く」) |

- 保存した定義は ML-ModelControl の `build_model` で `nn.Module` になり, ML-Found の学習スクリプトから使う

## 3. 画面

1. **部品の一覧** (左): 出どころごとに並べ, 名前と説明で検索する. 使えない部品 (ライブラリが無いものなど) は理由付きで選べない状態にする. 押すと見えている範囲 (か選んでいるものの右) に置き, キャンバスにドラッグすると落とした位置に置く (ドラッグでは線を引かない). 検索欄の Enter で, 使える部品のうち名前が一致するもの, 名前の終わりが一致するもの, 名前に含むもの, 説明に含むものの順に最初の 1 つを置く. 名前と説明のほかに, よく使う呼び方 (`global_mean_pool`, `dense`, `residual` など) でも探せる. 使えない部品の入れ方は `make setup EXTRAS="project ..."` で示す (既定の `project` を外さないため)
2. **キャンバス** (中央): ノード (部品), 入力, 出力を置き, 口から口へ線を引いてつなぐ. ノードには部品の名前, 口, 推定した出力の形, 誤りの印を出す (口の行にマウスを重ねると, 口の名前 (出力は形も) に登録簿の口の説明を付けて出す). 位置は定義の `ui` に保存する. 線とノードは選んで Delete か Backspace で消す. 幅 1536 px 未満の画面ではミニマップを出さない
3. **詳細** (右): 選んだノードの名前, 入力のつなぎ先 (選択の欄. ノードは新しい順. 登録簿に口の説明 (`op.Reparameterize` の `mu` は「平均」など) があれば, 引数の説明と同じく欄の下に出し, 欄の説明として読み上げる), 引数のフォーム (登録簿の説明と範囲付き. 種類と範囲に合わない値はその場で理由を出して反映しない. 選択肢は選択の欄, 真偽値か null だけを受け取る引数 (`Optional[bool]`) は未設定, true, false, null の選択の欄, 値の候補 (`suggestions`) は打ちながら選ぶ欄, 部品を受け取る引数は部品を選ぶ欄と入れ子の引数の欄 (下の「引数に書く部品」)), 一覧に無い引数 (`extra_params` の部品. 名前を書いて加える), 呼び出すときの設定の値, 入ってくる形 (つなぎ先ごと) と推定した出力の形とパラメータ数, 誤りと注意 (確認の誤りがあるノードは, 計算の誤りの文を重ねて出さない) を出す. 入力を選んだ場合は形, 型, 値の作り方を編集する. 何も選んでいない場合は全体の情報 (パラメータ数と学習するパラメータ数), 定義全体の誤り, 誤りと注意のあるノード (引数の不足, 出力に届かない, つなぎ先が 1 つの足し算など. 押すと選ぶ) と, 形の推定で失敗したノードと出力の一覧を出す
4. **上の操作**: 新規, 開く (保存した定義, 同梱の例と, 学習の実験の定義の写し (下の「実験の定義の写しを開く」). 保存した定義は消せる. 例の説明は数行になる (雛形は学習の step で行うことまで書く) ので, 行の間を空けて全文を出す. 読み上げでは例の名前をボタンの名前, 説明をボタンの説明にする. 部分モデルにする一覧も同じ), 保存 (開いたものと違う名前で既にある定義に保存する場合は確かめる), 元に戻す・やり直す, 整列, 入力と出力の追加, YAML と Python のコードの表示 (コピーとファイルのダウンロード), データセットとプロジェクト (下の「データセットとプロジェクト」), 明るさの切り替え. 保存すると少しの間, 画面の右下に「<名前> に保存しました」と出す (誤りがあれば「誤り n 件のまま」も). 幅 1280 px 未満ではアプリの名前と, 新規, 開く, パラメータ数の文字を隠して (アイコンと数だけにして) 1 行に収める. 全体のパラメータ数と誤りの数 (形の推定の失敗を含む) を出し, 大きすぎて形を推定しない場合は「形は未推定」と出す. 幅 1536 px 未満では整列, 入力, 出力, YAML, Python のボタンを, 幅 1800 px 未満ではデータセットとプロジェクトのボタンをアイコンだけにする

- **学習済みの重みのライセンス**: 学習済みの重みを読める部品 (ML-ModelControl の部品の一覧の `weights_params` が空でないもの. Hugging Face, timm, torchvision, segmentation_models_pytorch など) のノードの詳細に, 部品の説明の下に「学習済みの重みのライセンス」の欄を出す. ライセンスに関わる引数 (重みを読む引数と, モデルの名前, 版, 符号化器の名前と, 名前と版以外で重みを変える引数 (timm の `pretrained_cfg`, `pretrained_cfg_overlay`, `checkpoint_path` など. ML-ModelControl の `WEIGHT_OVERRIDE_PARAMS` に合わせる)) が落ち着いてから (0.6 秒) バックエンドに聞き (他の引数を変えても聞き直さない. 落ち着くまでの間は前の結果を出さず読んでいる途中と出す. ノードを選び直すと前のノードの結果は出さない), ML-ModelControl の `pretrained_info` が配布元 (Hugging Face のモデルの説明など) から読んだライセンス, 商用で使えるか, 説明, どこから読んだか (読めなかったか), 読んだ版, 重みの大きさ (人が読める単位. 1024 ごとに KB, MB, GB. 単位は丸めた後の値で決め, 1024 KB や 10.0 MB とは出さない. 負の値などの読めない値は出さない), 推論の一式に重みを写せるか, 表示の義務 (ライセンスが求める著作権の表示など), 出どころの表記の例 (作者, 置き場, 版, ページ, ライセンス), 配布元のページへのリンクを出す. 値の無いもの (大きさが分からない, 置き場が無い) は行ごと出さない. 商用で使えないものは誤りの色, 分からないもの (空, 独自の条件, 申請制, 読めなかった) は注意の色で「警告: …」とする (読み上げは控えめに `role="status"`. ノードを選ぶたびに割り込まないため). 重みを読まない引数 (`pretrained` を外すなど) では「今の引数では学習済みの重みを読みません」と出す. 部品の一覧では, 重みを読める部品の説明 (マウスを重ねた文) に, 置いた後の詳細でライセンスを確かめる案内を足す. 結果はバックエンドが覚え (読めたものは 1 日, 読めなかったものは 10 分), 画面も 10 分は聞き直さない. 非公開と申請制のモデルは, バックエンドを起動する環境の `HF_TOKEN` で読む. 通しのテスト (Playwright) は `HF_HUB_OFFLINE=1` で起動し, ネットワークを使わない
- **パラメータの状態 (定義の版 2)**: ノードの詳細の「呼び出すときの設定」の後に「パラメータの状態」の欄を出す (ML-ModelControl の定義の版 2 の `train`, `eval_mode`, `zero_init`, `weights`, `share`. 書き方と意味は ML-ModelControl の docs/DESIGN.md の「パラメータの状態」). 本体のノードと部分モデルの中のノードのどちらでも使える
    - 「学習する」(既定で入. 外すと `train: false` の凍結) と「評価の形のまま」(`eval_mode: true`. BatchNorm の統計と Dropout も止める. 凍結とは別に選び, 既定は外. 凍結した BatchNorm に書いていない場合は ML-ModelControl の注意 `frozen_norm_stats` を出す) のチェックの欄
    - 零初期化: 「しない」「全てのパラメータ」「名前を選ぶ」(カンマで区切った名前. 例: `weight, bias`. 部分モデルのノードは `nodes.fc.weight`)
    - 共有: 「しない」「ノード全体」(同じ部品のノードから選ぶ. 引数は同じ値を書く) 「パラメータごと」(1 行に `weight = embed.weight`). ノード全体を共有するノードは, 他の状態の欄を出さない (元のノードに従うため)
    - 外部の重み: 出どころ「読まない」「ファイル」(パス. 相対のパスは定義の置き場から) 「Hugging Face」(置き場の名前, ファイル, 版) 「学習済みの部品」(部品の名前と引数の JSON) と, 入れ物のキー (`state_key`), キーの付け替えの並び (1 行ごとに「前置き」か「正規表現 (番号の付け替え)」を選び, 前置き / 正規表現, 置き換え, 足す数 (正規表現だけ). 足す, 消す), 「合わない重みがあれば止める (strict. 既定で入)」のチェック. 既定の strict を欄の名前に出す
    - 「重みを読んで確かめる」ボタン: 定義全体を組み立てて外部の重みを実際に読み (`POST /api/weights`), 読んだノードごとに 読めた / 形の違う / 新しい / 使わない重みの数, 出どころ, ライセンス (Hugging Face と学習済みの部品から読んだ場合. 「学習済みの重みのライセンス」と同じ表示), 形の違うキーと新しいキーと使わないキーの一部を出す. 読めない場合 (ファイルが無い, strict で合わない, 1 つも読めない) は誤りの文を出す. 申請制の重みを読めなかった場合は, 誤りの型の名前を付けずに ML-ModelControl の日本語の理由と次にすること (トークンが無い, 無効, 申請が通っていない) を出し, 配布元のページへのリンクを添える (トークンが無いか申請が通っていない場合は「配布元のページで申請する」, トークンが無効な場合は「配布元のページを開く」. リンクにするのは `https://` で始まる URL だけ. バックエンドの設定の値をそのまま開かないため). ファイルとネットワークを使い, 重みも作るので, 編集のたびの確認 (`POST /api/check`) では読まず, ボタンを押したときだけ読む
    - 画面の中の定義は今の版 (2) で持ち, 版 2 の項目を使うと版を 2 にする (下書きや版 1 の空の定義に項目を足した場合). 保存と YAML の表示は ML-ModelControl の `dump_spec` が書ける最も低い版で書く (版 2 の項目を使わなければ版 1 のまま. 版 1 だけを読む古い学習のスクリプトでも読める)

- **データセットとプロジェクト**: ML-EDA (ML-Fathom) で書き出したデータセットと, ML-Quest (ML-Pathfinder) で書き出した学習のプロジェクトにつなぐ. 値をファイルから写し取る手間と写し間違いを無くすため. 上の操作の「データセットとプロジェクト」のダイアログに, 次の 3 つの欄を並べる. 殻で問題の設定を選んでいれば, 開いたときにそれを一覧から選んだのと同じく扱う (下の「殻で選んだ問題の設定」)
    - 「問題の設定から選ぶ」: ML-Pathfinder の置き場の問題の設定を, 更新の新しい順に並べる (名前, プロジェクトの場所, 更新時刻). 押すと, その problem.yaml を下の「プロジェクトに保存」の欄に入れて保存先を確かめ, 記録のデータセットの場所を「データセットから入力と出力を作る」の欄に入れる (欄に打った後でも入れる. 選んだ問題の設定のものにそろえるため). プロジェクトの場所を打たずに, 問題の設定から入力と出力を作って保存できるようにするため
        - 受け持ちに合う雛形 (`handoff` の `model.example`) がある問題の設定は, 一覧に雛形の名前を添える. 選んだとき, 新しく始める場合 (今の定義に部品, 出力, 部分モデルが無く保存していない変更も無い, かつ保存先にまだ定義が無い) は, その雛形 (ML-ModelControl の `load_example`. 「開く」の同梱の例と同じ) を開き, 一覧の下に「問題の設定 <問題の設定の名前> の受け持ちに合う雛形 <名前> を開きました. 入力と出力はデータセットから作れます」と出す (知らせはダイアログの中だけに出す). 既に定義がある場合は開かずに, 理由 (保存していない変更がある, 今の定義がある, 保存先に定義が既にある) と「雛形 <名前> を開く」を出して選べるようにする. 押すと, 保存していない変更がある場合は捨ててよいかを, 今の定義がある場合は雛形で置き換えてよいかを確かめる. 場所を打って確かめた問題の設定も, 開かずに選べるようにする. 問題の設定の受け持ちから始める定義を選び直す手間を無くし, 今の定義を黙って捨てないため. 雛形を開いてもダイアログは閉じず, 保存先, データセットの場所と保存する名前は変えない (続けて入力と出力を作り, 保存できるように). 雛形を開くと履歴を消し, 保存していない変更のある定義にする (まだどこにも保存していないため. 閉じるときに確かめ, 下書きにも残す). 雛形の無い問題の設定 (一から学習しない, 合う雛形が無い) は今までどおり. 雛形の名前は今の ML-ModelControl の同梱の例にあるものだけを渡す (開けない雛形を出さないため). どの受け持ちにどの雛形が合うかは ML-Quest の `model.example` が決め, このアプリは名前を受け取って開くだけ (受け持ちと雛形の対応を 1 か所にまとめるため). 異常の検知の自己符号化器の雛形は表の行の自己符号化器 `tabular_autoencoder` で, 距離に基づく度合いはモデルの定義が要らないので雛形を出さない. 効果を見積もる (今ある記録から顧客ごとの効果を見積もる) の雛形は表の行の効果のモデル `tabular_uplift` (処置の群と対照の群で 2 つの予測を学ぶ T-learner) で, 方策の効果を見積もる受け持ちには雛形を出さない. 値段を変える判断 (効果を見積もるで, 試しに値段を変えた売れ行きの記録から, 決めた値段の候補の中で利益が最も大きい値段を商品ごとに選ぶ) の雛形は表の行の売れ行きのモデル `tabular_price` (値段を入力の最後の列に入れ, 売れた数の予測 `units` を出す). 時間をまたぐ量の判断 (予測するで正解の種類が先の期間の需要. 商品ごとの日ごとの売れた数の記録から先の期間の需要を分位点で予測し, 品切れの損と売れ残りの損の比から決まる分位点で発注の数を商品ごとに決める) の雛形は表の行の需要の分位点のモデル `tabular_demand` (先の期間の需要の分位点を, 学ぶ水準の小さい順に `quantiles` に出す)
        - 使えるのは, 保存先を「プロジェクトに保存」と同じ決め方で決められるもの (プロジェクトを書き出した記録とモデルの定義の置き場の記録があり, 記録のプロジェクトが今もある). 他 (書き出していない, 書き出してあるが定義の置き場の記録が無い, 読めない, 問題の設定のファイルでない, プロジェクトを移したか消した) は理由を付けて並べ, 選べなくする. 記録の無い理由はプロジェクトの場所の記録 (`project.path`) の有無で分ける (書き出したプロジェクトを「書き出していません」と出さないため. 定義の置き場の記録が無いものは, プロジェクトのディレクトリを選ぶと保存できることを添える). 異常の検知で度合いの決め方が距離に基づく度合い (ML-Quest の受け渡しの `anomaly.score` が `distance`) のものは, 学習しないので「モデルの定義は要りません」を理由にする (定義の置き場の記録が無いのはモデルを使わないためで, 保存先を選び直す話ではないため). 置き場が無ければ, 置き場の場所と下の欄で選べることを出す
    - 「データセットから入力と出力を作る」: データセットのディレクトリの場所を書き (前に読んだ場所が入る. 下の欄でプロジェクトの保存先を確かめると, この欄に打つ前ならその記録のデータセットの場所 (記録の無いプロジェクトは骨組みの config の `data.dataset` をプロジェクトのディレクトリから求めた場所. 学習のスクリプトが読む場所と同じにするため) が入る), 押すとバックエンドが ML-EDA の `model_inputs` で読む. 下の欄で問題の設定から保存先を確かめていれば, その問題の設定のファイルも渡す. 結果は本体の定義に 1 回の変更として入れる (元に戻すで戻せる. 部分モデルを編集している間は理由を出して選べない)
        - 雛形のままの定義: 本体の定義が ML-ModelControl の書き換えられる雛形 (`TEMPLATE_ARGS` にある同梱の例) のままなら, ノードの名前と引数をたどって決めずに, 雛形の書き換える引数 (ML-ModelControl の docs/DESIGN.md の 9 節の表) の値をデータセットから決めて, ML-ModelControl の `adapt_example` が返す定義を使う (雛形ごとの書き換える場所を ML-ModelControl の 1 か所にまとめ, 雛形を直したときに画面の決め方だけが古くならないため). その後の入力の形と型は下の入力の決まりのまま入れ, 下の入力に直につながるノードと出力の大きさの決まりは当てない. 雛形の入力の名前は変えず, 雛形の入力と名前の違うデータセットの入力は定義に入れずに知らせる (雛形の入力の名前は学習のスクリプトとの約束で (ML-ModelControl の docs/DESIGN.md の 9 節), 変えると次に入れるときに雛形と見分けられなくなるため)
            - 雛形のままかは, バックエンドが雛形ごとに照らして決める. 書き換える引数の今の値を定義から読み (引数の最初の場所の値を倍率で割る), その値で `adapt_example` した定義と, 位置 (`ui`), 定義の名前と説明, 入力の形と型を除いて同じなら, その雛形とみなす (「開く」の例, 問題の設定の雛形, 保存して開き直した定義を同じに見分け, 一度データセットから入れた雛形にも入れ直せるようにするため. 入力の形と型はデータセットから入れ直すので照らさない). 部品か引数かつなぎ方か入力の名前を変えた定義, 書き換えられる雛形の無い同梱の例と自分で組んだ定義は雛形でないとみなし, 下の決まりでノードをたどって決める
            - 引数の値: 入力の形の軸に書く引数 (入力の幅, 利用者と品物の数, チャンネル数, 入力の点の数など) は, 同じ名前のデータセットの入力 (定義の入力とデータセットの入力が 1 つずつなら, 名前の違う入力. 撮影の入力 `capture` から点群の雛形の `observed` の点の数を決めるなど) のその軸の大きさにする. 次元の数が雛形の入力と違うデータセットの入力からは決めずに知らせる (違う形の軸の大きさを書かないため). `gan_generator` の雑音の幅 `noise` はデータの幅でないので決めずに知らせ, 出す 1 行の幅 `features` を, データセットの 2 次元の入力 1 つの 2 番目の大きさにする. 出す値の数の引数は, `unet_segmentation` の `classes` と `point_cloud_predictor` の `points_out` をデータセットの出す値の数に, `tabular_demand` の `levels` を学ぶ分位点の水準の数 (下の時間をまたぐ量の判断の決まり) にする. データセットで決まらない軸, 分からない出す値の数と水準, データセットから決めない引数 (縮めた幅, 潜在の幅, 雑音の幅, 行動の数) は今の値のまま渡す (今の値を `adapt_example` に渡すので, 前に入れた値も残る)
            - 返った定義には, 今の定義の位置, 名前と説明と, 入力の形の書き換えない軸と型を残す (雛形の同梱の位置に戻して, 並べ直した配置を崩さないため)
            - 照らすか書き換えるのに失敗した場合 (バックエンドの誤り) は, 雛形でない定義の決め方で入れ, 理由を知らせる (読んだデータセットを捨てないため). データセットを読む間 (照らし合わせと書き換えの間を含む) に本体の定義が変わった場合は, 雛形かどうかに関わらず何も変えずに, もう一度押すよう知らせる (読む前の定義から作った結果で, 変えた定義を戻さないため)
            - 知らせは, 雛形の名前と ML-ModelControl の書き換えで合わせたことを 1 行, 渡した引数ごとに前と後の値と書き換えた場所 (入力の形の何番目, ノードの引数. 倍率は × で添える) を 1 行ずつ出す (同じ値なら「のまま」). 種類ごとの決め方の知らせ (表の生成, 並べる, 異常の検知, 効果の見積もり, 値段を変える判断, 時間をまたぐ量の判断) は雛形でない定義と同じに初めに, 値段を変える判断, 効果の見積もりと並べるの出力の大きさを変えない知らせは終わりに出す. 出力の大きさが雛形の決まりで決まる雛形 (`vae`, `tabular_autoencoder`, `diffusion_denoiser`, `gan_discriminator`, `gan_generator`, `contrastive_encoder`, `policy_value`) にデータセットの出す値の数がある場合は, それを使わない理由 (再構成は入力と同じ幅など) を終わりに出す (表の生成と異常の検知は出す値の数が入力の幅と同じで, 初めの知らせに決め方を出すので除く). 時間をまたぐ量の判断の `levels` は, 水準と, どこから読んだかを添えて出力 `quantiles` の値の数として知らせる
        - 入力: データセットの入力の名前, 形, 型にする. 形のバッチの次元 (`null`) は例の大きさ 4 にする (形の推定の例にだけ使うため). 他の決まらない次元 (大きさの混ざる画像の高さと幅など) は, 定義の入力が同じ次元の数の形を持てばその値のまま, 無ければ 4 にする (同梱の例の 4 の倍数の大きさを壊さないため). API は例の形 (`shape`) とデータセットの形 (`dataset_shape`. 決まらない次元は `null`) の両方を返す. 定義の入力とデータセットの入力が 1 つずつで名前が違えば, 名前を変えてつなぎ先も書き換える. 同じ名前の入力は形と型だけを変え, 値の作り方と位置は残す. データセットに無い入力は, つないでいなければ消し, つないでいれば残して知らせる. 残す入力の最初の次元は, 定義の入力 (0 次元の値を除く) の最初の次元が全て同じで, そのうちの 1 つ以上がデータセットの入力と同じ名前 (名前を変えた後) で, データセットの入力どうしの最初の次元も同じ場合だけバッチとみなし, 例の大きさ 4 にそろえて, 残した知らせに添える (「最初の次元 (バッチ) を例の大きさ 4 にしました」) (時刻の入力などのバッチがデータセットの入力と合わずに形の推定が止まるのを防ぎ, 最初の次元がバッチでない固定の形の値を変えないため). 他 (最初の次元が違う入力がある, データセットの入力と同じ名前の入力が無い, データセットの入力どうしの最初の次元が違う) は形を変えない. データセットの入力と同じ名前のノードがある場合は, 何も変えずに知らせる (つなぎ先が入力を指すように変わるため)
        - 雛形でない定義では, 入力に直につながる, `in_features` の引数を持つノード (`nn.Linear` など) は, `in_features` を入力の最後の次元にする. `in_channels` の引数を持つノード (`nn.Conv2d` など) は, 3 次元以上の入力の 2 番目の次元 (チャンネル) にする. `num_embeddings` の引数を持つノード (`nn.Embedding`) は, 文の語の番号の入力なら語彙の大きさ (ML-EDA の `model_inputs` の入力の `vocabulary`. API も同じ名前で返す) にする (語彙より小さい埋め込みは学習の途中で番号が表の外になって止まるため)
        - 出力の大きさ (`outputs`. 分類はクラスの数, 回帰は 1, 予測は先の期の数か 1. 異常の検知は学習に使う列の数. 効果を見積もるは 1. 値段を変える判断は 1 (売れた数の予測. 下の値段を変える判断の決まりのとおり変えない). 時間をまたぐ量の判断は学ぶ分位点の水準の数 (下の時間をまたぐ量の判断の決まり). 画像と領域は背景を含む領域のクラスの数, 点群は出す点の数): 雛形でない定義に入れる. 部品の無い定義で入力が 2 次元なら, `nn.Linear` の `head` を置いて出力 `out` につなぐ. 出力が 1 つで, そのつなぎ元のノードが `out_features` か `out_channels` (画素ごとのクラスのスコアを出す畳み込み. 同梱の例 `unet_segmentation` の `head`) の引数を持てば, それを出す値の数にする. つなぎ元が `op.Reshape` で, その 1 つ前のノードが `out_features` を持てば, `shape` の最初の次元を出す値の数にし, 前の `out_features` を `shape` の全ての次元の積にする (点の数 × 3 を出して並べ直す形. 同梱の例 `point_cloud_predictor` の `decode2` と `cloud`). それ以外 (出力が複数, 最後がこれらを持たない部品, タスクを決めていない) は変えずに, 手で入れる値を知らせる
        - 表の生成 (作るで, 正解の種類が表) の問題の設定を渡した場合: 入力の列の次元と出す値の数を, ML-Quest の `table_encoding` の符号化した行の幅 (数の列は 1, 種類の列は値の種類の数の和) にする. 表の生成の骨組みの学習のスクリプトは, 列の数でなくこの幅の行を学ぶため (ML-Quest の `table_encoding` と, 書き出すスクリプトに写した同じ決まりで求める). 雛形 `diffusion_denoiser` では, 入力 `x` の形と `x_fc` の `in_features`, 出力 `noise` のつなぎ元 `head` の `out_features` が幅になる (時刻の入力 `t` はデータセットに無いがつないでいるので残し, 最初の次元を `x` と同じ例の大きさ 4 にそろえる). 決め方 (幅, 数の列と種類の列の数, 種類の値の数の和, 列の数) は入れた結果の初めに知らせる. 幅を求められない場合 (目的の列か欠損のある列がある, 種類の値が 100 を超える列がある, 予測の表の列と重なる名前の列がある) と, 入力が表の行 (2 次元の 1 つ) でない場合は, 理由を出して何も変えない. 画面の文は「学習で使う 1 行の長さ」(数の項目は 1 つずつ, 分類の項目は選べる値の数の合計) と言う (符号化を知らない利用者にも分かるように). 表の生成でない問題の設定と, 問題の設定を渡さない場合は列の数のまま
        - 並べる (反応の表で 2 塔のモデルを学ぶ) の問題の設定を渡した場合: 欄の場所は ML-EDA のデータセットでなく反応の表のファイル (記録の `data.project_dataset`. 学習のスクリプトの config の `data.dataset`) で, ML-EDA の `model_inputs` は使わない. ML-Quest の `rank_encoding` で学習用の利用者と品物の数を求め, 入力を `user` ((4, 利用者の数)) と `item` ((4, 品物の数)) の float32 (利用者と品物の番号のワンホット. 学習のスクリプトと同梱の例の入力の名前) にする. 学習のスクリプトは反応を時刻の順に分け, 学習用の反応にいる利用者と品物だけに番号を付けるので, 反応の表の全ての利用者と品物の数とは違うため (ML-Quest の `rank_encoding` と, 書き出すスクリプトに写した同じ決まりで求める). 分ける割合は, 問題の設定が記録したプロジェクトの `configs/default/train.yaml` の `data.valid` と `data.test` があればそれ, 無ければ学習のスクリプトの既定 (学習で使う割合にそろえるため. 起動のときの config の差分は見ない). config があるのに読めない場合は既定の割合で求め, 「学習の設定 (`configs/default/train.yaml`) を読めないので, 分ける割合は既定の値です」と知らせる. 並べるかは受け持ちの答え (ML-Quest の `active_value` の `role`) で先に見て, 並べる以外では `rank_encoding` を読まない (`rank_encoding` の無い古い ML-Quest でも, 表の生成と列の予測を止めないため. 並べるで無ければ 501). 雛形 `two_tower_retrieval` では, 入力 `user` と `item` の形と, 1 段目の全結合 `user_fc1` と `item_fc1` の `in_features` が数になる. 出力 `score` は全ての組の点数の表なので大きさは変えない. 決め方 (利用者と品物の数, 学習用の反応の行の数, 分ける割合 (config の値か既定)) と, 除いた行の知らせ (欠けた行, 反応の強さが 0 以下の行) は入れた結果の初めに知らせる. 反応の表が無い場合と, 数を求められない場合 (列が無い, 時刻を読めない, 割合の誤り, 学習用か検証用が空になる) は, 理由を出して何も変えない. 画面の文は「学習用の利用者の数」「学習用の品物の数」と言い, 検証用とテスト用にだけ出る利用者と品物は数えないことを添える
        - 異常の検知のデータセット (ML-EDA の `task: anomaly`): ML-EDA の `model_inputs` の `outputs` は学習に使う列の数 (正解の列と行の id の列は数えず, `one_hot` で増えた列は数える) で, 入力 `x` の最後の次元と同じ. 自己符号化器は入力を作り直すので, 出力の大きさもこの数にする (上の入力と出力の大きさの決まりのまま入る). 雛形 `tabular_autoencoder` では, 入力 `x` の形と `enc1` の `in_features`, 出力 `recon` のつなぎ元 `dec2` の `out_features` が列の数になり, 縮めた幅 (`enc2` の `out_features`, `dec1` の `in_features`) は変えない. 決め方 (学習に使う列の数, 出力を入力と同じ幅にしたこと, 正解の列があればそれを数えないこと) は入れた結果の初めに知らせる. 「自己符号化器」と言うのは, 問題の設定の度合いの決め方が自己符号化器の場合だけ. 問題の設定を渡さない場合と, 度合いの決め方にまだ答えていない場合も同じ幅を入れる (ML-EDA が異常の検知の出す値の数を学習に使う列の数と決め, 他のタスクの出す値の数と同じく入れるため) が, 知らせはデータセットの決まりとして出し, 未回答ならそのことを添える (選んだモデルを自己符号化器と決めつけないため). 問題の設定を渡した場合は, 受け持ちが異常の検知 (予測するで正解の種類が異常. ML-Quest の `active_value` で読む) かを見て, 度合いの決め方 (`anomaly.score`) を読む. 距離に基づく度合い (`distance`) は学習せずモデルの定義が要らないので, そのことを知らせて何も変えない. 異常の検知の問題の設定で, データセットが異常の検知の表でない場合は, 理由を出して何も変えない (骨組みの学習のスクリプトは異常の検知の表を読むため)
        - 効果を見積もるのデータセット (ML-EDA の介入の記録の表 `task: uplift`): ML-EDA の `model_inputs` の入力 `x` の最後の次元は学習に使う列の数 (処置の列, 結果の列と行の id の列は数えず, `one_hot` で増えた列は数える) で, `outputs` は 1 (出力の頭 1 つが 1 件に出す値の数). 入力の幅は上の入力の決まりのまま入る. 出力が 2 つ以上 (T-learner の処置したときの予測 `treated` としないときの予測 `control`) の場合は, 出力ごとにつなぎ元の `out_features` を 1 にする (出力が 1 つの場合の決まりを, 頭ごとに当てるため). つなぎ元が `out_features` を持たない出力は, 手で入れるよう知らせる. 雛形 `tabular_uplift` では, 入力 `x` の形と `treated1` と `control1` の `in_features` が列の数になり, `treated2` と `control2` の `out_features` は 1 のまま, 隠れ層の幅 (`treated1` と `control1` の `out_features`, `treated2` と `control2` の `in_features`) は変えない. 決め方 (学習に使う列の数, 入力に入れない処置の列, 結果の列と行の id の列, 効果の見積もりの 2 つの出力がどちらも 1 つの値を出すこと) は入れた結果の初めに知らせる. 処置や結果の語を知らない人にも分かるよう, 入力に入れない列には役を言葉で添える (処置は行動したかどうか, 結果は行動の後にどうなったか, id は行を見分ける列). 処置の列と行の id の列の名前は, データセットの説明の `uplift.treatment` と `uplift.id` (ML-EDA の `load_dataset` で読む. ML-EDA の `model_inputs` は返さないため) を先に使い, 無ければ問題の設定の答え (`uplift.treatment` と `uplift.id`. ML-Quest の `active_value` で読む) から出す (知らせる名前を, 実際に入力から除いた列にそろえるため). どちらにも無ければ名前を出さずに役だけを出す. 問題の設定を渡した場合は, 受け持ちが効果の見積もり (効果を見積もるで, 方策でなく, 今ある記録から集め, 作り方が既製のモデルをそのままでなく, 記録で変えたもの (`varied`) が値段でない. ML-Quest の効果の見積もりの受け持ちと同じ見分け方) かを見る. 効果の見積もりの問題の設定で, データセットが介入の記録の表でない場合は, 理由を出して何も変えない (骨組みの学習のスクリプトは介入の記録の表を読み, 処置の列を入力から除くため)
        - 値段を変える判断のデータセット (ML-EDA の値段を変えた記録の表 `task: price`): ML-EDA の `model_inputs` の入力 `x` の最後の次元は, 商品の特徴の列と値段の列の数 (学習に使う列で, 値段の列はその最後. 売れた数の列, 元の値段の列, 原価の列, 商品の id の列と行の id の列は数えず, `one_hot` で増えた列は数える) で, `outputs` は 1 (売れた数の予測 `units` が 1 件に出す値の数). 入力の幅は上の入力の決まりのまま入る. 出力の値の数は 1 のまま変えない (売れた数の予測は常に 1 つの値で, ML-ModelControl の docs/DESIGN.md の 9 節の `tabular_price` の書き換える引数に入らないため. 上の出力の大きさの決まりは当てない). 雛形 `tabular_price` では, 入力 `x` の形と `units1` の `in_features` が列の数になり, `units2` の `out_features` (1) と隠れ層の幅 (`units1` の `out_features`, `units2` の `in_features`) は変えない. 決め方 (特徴の列と値段の列の数, 値段の列が入力の最後の列であること, 入力に入れない売れた数の列, 原価の列, 商品の id の列と行の id の列) は入れた結果の初めに, 出力の値の数を変えないことは終わりに知らせる. 初めての人にも分かるよう, 列には役を言葉で添える (値段は商品の売り値, 売れた数は予測する値, 原価は仕入れか作るのにかかる値段で利益の計算に使う, 商品の id は値段を選ぶ単位, id は行を見分ける列). 値段, 原価, 商品の id と行の id の列の名前は, データセットの説明の `price` (`price`, `cost`, `product`, `id`. ML-EDA の `load_dataset` で読む) を先に使い, 説明にその項目が無ければ問題の設定の答え (`price.price`, `price.cost`, `price.product`, `price.id`.         - 問題の設定のファイルか, プロジェクトの中の `problem.yaml`: ML-Quest の `handoff` の `model.project_model_spec` (ML-Quest が骨組みを書き出したときの記録). 記録のプロジェクトの場所 (`project.path`) が学習のプロジェクト (`configs/default/train.yaml` を持つ) で, その中の場合だけ書く (手で書いた記録や, 移したか消したプロジェクトの記録で, よその YAML を書き換えないため)
        - 記録の無いプロジェクト (`configs/default/train.yaml` を持つディレクトリ): config の `model.spec` (書いていなければ骨組みの既定の `models/model.yaml`. 学習のスクリプトが読む場所に書くため. リンクをたどった先もプロジェクトの中に限る)
        - プロジェクトの中の `problem.yaml` を読めない場合 (ML-Quest が無い, 知らない版, 直すところがある) は, 既定の場所に替えずに理由を出して止まる (記録と違う場所に黙って書かないため)
        - 保存先が学習の設定のディレクトリ (プロジェクトの `configs/` の中. `configs/default/train.yaml` も) なら, 理由を出して書かない (config の `model.spec` の書き間違いで, 学習の設定を消さないため. 大文字と小文字は区別しない)
        - 保存先がプロジェクトの直下の `problem.yaml` か, `data/` か `outputs/` の中なら, 理由を出して書かない (ML-Quest が書き出した問題の設定の写しと写したデータ, ML-EDA が書き出したデータセット (`outputs/dataset`) と ML-Found の実験のディレクトリ (`outputs/`) を, モデルの定義で上書きしないため. 大文字と小文字は区別しない). `outputs/` は ML-Found の既定の出力先の名前で, config の `experiment.output_dir` で変えたプロジェクトでも既定の名前で判定する
        - 保存先までの途中の名前がディレクトリでない (ファイルなど) なら, 理由を出して書かない (確かめが通った後に, 保存でディレクトリを作れずに失敗しないため)
        - 保存先の拡張子が小文字の `.yaml` か `.yml` でない (`A.YAML`, `a.Yml` など) なら, 理由を出して書かない (ML-Dashboard の「モデルの定義の候補」は小文字の拡張子のファイルだけを並べるため). 大文字と小文字を区別しないファイルシステムで, 名前の保存先が大文字の拡張子の既にあるファイルになる場合も同じで, ファイルの名前を直すように出す
        - 「models/ の下の名前」を書くと, 上で決めたプロジェクトの `models/<名前>.yaml` に保存する (空なら上の既定の保存先). モデルの候補を並べるため (ML-Dashboard の学習の起動の「モデルの定義の候補」は, プロジェクトの `models/` の下の YAML を一覧にする). 名前は置き場の名前と同じ規則 (英数字, `_`, `-`. 先頭に `-` は使えない. 64 文字まで) に限り, 中のディレクトリは作らない (`/` を受け取らないことで, `models/` の外と `..` を断つため). `models/` かそのファイルがリンクなら, 理由を出して書かない. 問題の設定の記録の保存先がプロジェクトの外なら, 名前を書いても理由を出して書かない (記録を信じられないため)
            - 同じ名前の `<名前>.yml` が既にあり `<名前>.yaml` が無ければ, `.yml` の方を保存先にして上書きを確かめる (ML-Dashboard の候補に同じ名前を 2 つ並べないため). 大文字と小文字だけ違うファイルを同じファイルとして扱うファイルシステムでは, 保存先と確かめの文に実際のファイル名を出す
            - 名前の保存先が既定の保存先と同じファイルなら, 既定の定義を上書きすることを添える. どちらもまだ無い場合は場所の文字で比べ, 大文字と小文字だけ違う場合は, 置き場が大文字と小文字を区別しないとき (一番近いある上のディレクトリの名前を, 大文字と小文字を入れ替えて探して見分ける. 見分けられる名前が無ければ区別しない扱い) だけ同じファイルとみなす (書くと既定の定義と同じファイルになるため). 確かめた後に場所か名前を書き換えたら, 確かめ直すように出す. 確かめに失敗した場合 (名前が規則に合わない, 書けない保存先など) は誤りだけを出し, 前に確かめた保存先, 一覧の問題の設定の選択も消す (書き換えたように読めて迷わせないためと, 失敗した場所に前の保存先のまま書かないため). 確かめが重なった場合 (確かめの間に一覧から選んだ場合) は, 最後に送った確かめの結果だけを出す (遅れて返った前の結果で, 後の結果を上書きしないため)
        - config の `model.spec` は書き換えない. ML-Dashboard が候補ごとに書き換えて学習するためで, 既定の定義はプロジェクトの `configs/default/train.yaml` の `model.spec` のまま

        - 既にファイルがある場合は, 上書きしてよいかを確かめてから書く. 保存の要求には確かめた保存先を添え, 書くときに決め直した保存先と違えば書かない (上書きの許しを確かめた保存先にだけ効かせるため. 確かめた後に同じ名前の `.yaml` が作られた場合や, config の `model.spec` が変わった場合). 保存が断られた場合 (保存先が変わったか, 確かめた後に他でファイルが作られた) は, 保存先を確かめ直して理由を出し, 見直してから押し直すようにする (確かめていない保存先と, 既にあると知らせていないファイルに書かないため). 保存するのは定義全体 (置き場への保存と同じく `dump_spec` が書ける最も低い版). 置き場の定義とは別のファイルなので, 置き場の保存していない変更の印 (`*`) は変えない. 保存すると欄の下と画面の右下に「<保存先> に保存しました」と出す

            - 約束と比べ方は ML-Quest の `model_contract` と `check_model_contract` が持ち, このアプリには写さない (骨組みを書き出す持ち主の 1 か所にまとめるため). ただし出力の形の大きさは, 下のとおりこのアプリで比べる (定義の出力の形を求めるには形の推定が要り, それを持つ ML-ModelControl をこのアプリが使うため. ML-Quest の約束の数はそのまま使う). 約束の無い骨組み (入力の形をデータセットで決める列の予測など, 機械学習を使わない場合) と, 記録の無いプロジェクトのディレクトリ (問題の設定が無い) は確かめない
            - 最後の大きさの数は, バックエンドが記録のデータセットと問題の設定から, 「データセットから入力と出力を作る」と同じ読み方で求める (表の生成は符号化した行の幅, 並べるは学習用の利用者と品物の数, 異常の検知, 効果の見積もり, 値段を変える判断, 時間をまたぐ量の判断は入力の幅にした学習に使う列の数. 骨組みの型と同じ意味の数だけを使い, 他の骨組みの最後の大きさは約束の数だけで見る). 時間をまたぐ量の判断の出力 `quantiles` の値の数にする学ぶ分位点の水準の数は, データセットに依らず, 「データセットから入力と出力を作る」と同じ決め方 (記録のプロジェクトの学習の設定の `demand.levels` が先, 無ければ問題の設定の受け渡し) で求める (学習のスクリプトが読むのは学習の設定の水準で, データセットを読めない場合も問題の設定の水準で比べて誤って断らないため). 画面から数を送らないのは, 入力と出力を作らずに保存した場合も, 記録のデータセットの数で確かめるため (欄に別のデータセットを書いて作った定義は, 記録のデータセットと数が違えば合わない所になる). データセットの場所の記録が無いか読めない場合は, 名前と出力の数, 約束で決まる大きさ (効果の見積もりと値段を変える判断の出力の 1) と学ぶ水準の数だけを確かめ, データセットで決まる大きさを確かめていないことを知らせる (確かめの助けの数なので, 保存は止めない). データセットを読めても求められない数 (方策の観測と行動の数, 群分けの符号化した行の幅など. 約束にも数の無いもの) は, その入力か出力の最後の大きさを確かめていないことを入力と出力ごとに知らせる (確かめたように読めて迷わせないため)
            - 出力の形の大きさ: 定義の出力は形を持たない (出どころのノードの名前だけ) ので, バックエンドが ML-ModelControl の形の推定 (`infer`. 編集の画面の形の推定と同じ) で定義の出力の形を求め, 約束の出力の項目の数 (上の求めた数が先, 無ければ約束の `size`) と比べる (異常の検知の `recon` は学習に使う列の数, 効果の見積もりの `treated` と `control` は 1, 値段を変える判断の `units` は 1, 時間をまたぐ量の判断の `quantiles` は学ぶ水準の数, 表の生成の雑音の予測は符号化した行の幅). 比べ方は骨組みの学習のスクリプトの読み方に合わせる. 効果の見積もり, 値段を変える判断, 時間をまたぐ量の判断の骨組みは出力を (件数,) か (件数, 数) に reshape して読むので, バッチの次元 (最初の次元) を除いた大きさ (残りの次元の大きさの積. (件数,) の形は 1) で比べる ((件数,) の `treated` や (件数, 水準の数, 1) の `quantiles` も学習できるため). 異常の検知の再構成と表の生成の雑音の予測は, 骨組みが出力をそのまま入力と同じ形として使うので, (件数, 数) の 2 次元で最後の大きさが合うことを求める (積が合っても (件数, 列の数, 1) などは学習で食い違うため). 直し方の文は, (件数, 数) の形なら最後の大きさ, 他の形なら推定した形を添える (reshape して読む骨組みは積も). 入力の形は定義のままで推定する (入力の幅の誤りは入力の直す場所に出るので, 推定を止めずに出力の大きさも出すため). 合わない所は ML-Quest の直す場所と同じ形 (`level`, `id` は `outputs.<名前>`, `message`) で入力の直す場所の後に並べる. 学習の設定の水準を増やして水準の数を変えない定義などを, 学習を始める前に見つけるため. 名前の無い出力と, 名前を問わない出力の数が約束と合わない場合は, 当てる出力が決まらないので比べない (名前と数の直す場所が出る). 形を推定できない出力は, 大きさを確かめていないことを出力ごとに理由を添えて知らせる (確かめの助けなので, 保存は止めない). 理由は, 出力そのものの誤り, 出どころのノードの誤り, 推定の上限 (パラメータ数か入力の例の要素数), 定義の誤りの順に選ぶ. 推定できてもテンソルでない出力 (タプルや辞書) とバッチの次元の無いテンソルは, そのことを知らせて確かめない
            - 合わない所があれば書かずに, 欄の下に「骨組みの入力と出力に合わない所」として, 直す場所 (`inputs.x` など) と直し方の文を並べる. 書くかどうかは利用者が選び, 「直さずに保存」で同じ保存先にそのまま書ける (骨組みを手で直して学習する場合があるため. この保存では確かめない). 押すと欄が消えるので, focus を保存の結果の文に移す. 断られた後 (保存の間も含む) に定義を書き換えた場合は, 合わない所の代わりに, 書き換えたのでもう一度保存するように出す (何も出ずに保存されたように読めるのを避けるため). 定義を書き換えるか保存先を確かめ直すと, 並べた所を消す. データセットから入力と出力を作った雛形は合うので, 何も出さない
        - 最後に確かめたプロジェクトの場所とデータセットの場所は, ブラウザ (`localStorage`) に覚えて次の欄に入れる. `models/` の下の名前は覚えない (候補ごとに変える名前なので, 前の名前のまま保存して別の候補を上書きしないため)
- **自作の部品 (起動の設定のモジュール)**: 研究の自作の部品は, バックエンドを起動する環境の `ML_CREATEARCHITECTURE_MODULES` (モジュールの名前をカンマで区切って並べる. 例: `my_lab.units,my_lab.blocks`) に書いたモジュールだけを, 起動のときに ML-ModelControl の `register_units_from` で読み込む (宣言の書き方は ML-ModelControl の docs/DESIGN.md の「自作の部品のモジュール」). このリポジトリの他の起動の設定 (`ML_CREATEARCHITECTURE_HOME`, `ML_CREATEARCHITECTURE_TOKEN`, `ML_MODELCONTROL_WEIGHTS_DIRS`) と同じく環境変数にし, 設定のファイルは作らない
    - 起動のログに, モジュールごとに読み込んだ部品の名前を出す (「自作の部品を読み込みました: my_lab.units → my.Block, my.Pair」). 読み込めないモジュールがあれば, 理由を出して起動を止める (書き間違いに気付かないまま, 定義が「登録されていない」誤りになるのを避けるため)
    - 部品の一覧では, 自作の部品をモジュールごとに「自作 (my_lab.units)」のまとまりにし, 組み込みの部品の後に置き, 開いた状態で始める (Python のコードから直に登録した部品は「自作」)
    - 登録されていない部品を使う定義 (自作の部品の定義を, そのモジュールを書かずに起動したアプリで開いた場合など) では, そのノードの誤り (ML-ModelControl の `unknown_unit`) の下と, 何も選んでいない場合の全体の情報に, 部品を宣言したモジュールの名前を起動の設定 `ML_CREATEARCHITECTURE_MODULES` に足して起動し直す案内, 起動の例, 今読み込んでいるモジュールの一覧 (`GET /api/modules`) を出す. 定義に書いた名前からは何も読み込まない. 画面の型を作るための仕様の書き出し (`--openapi`) ではモジュールを読み込まない
    - 画面, API, 定義のファイルからはモジュールを選べない (起動する人だけが選ぶ). 書いたモジュールは起動のときに任意のコードとして動くので, 信頼できるコード (自分や仲間が書いたもの) だけを書く
- **左右の欄**: 部品の一覧と詳細は, キャンバスの左上と右上のボタンで畳める. 幅 1200 px 未満の画面では畳んで始める. `/` で部品を探すと左の欄を開き, キーボードで部品を置くと詳細を開いて引数の最初の欄 (無ければ入力のつなぎ先) に移る
- 編集するたびに (少し待ってから) バックエンドで確認と形の推定をし, 結果をノードに重ねる
- キャンバスの線は定義の各ノードの `inputs` と 1 対 1 に変換する (可変の数の口は, 線を引いた順がリストの順)
- **元に戻す・やり直す** (Delete キーで消した線とノードは 1 回分. やり直しは Ctrl+Shift+Z か Ctrl+Y, Mac は Cmd): 定義を履歴付きの値で持つ (上限 100 回). 同じノードのドラッグの続けての移動は 1 回分にまとめ, 中身の同じ変更は残さない. 定義を開くか新規にすると履歴を消す. Ctrl+Z (Mac は Cmd+Z) と Ctrl+Shift+Z (か Ctrl+Y), 文字を打つ欄の中では, 打ちかけの文字がある間はブラウザの標準の取り消し, 値を反映した後 (打ちかけの文字が無い間) は定義を戻して欄にも出す
- **下書き**: 保存していない変更は, 少し待ってからブラウザ (`localStorage`) に画面 (タブ) ごとの下書きとして残す (書けない場合は古い下書きを残さないように消す). 次に開いたとき, その画面の下書き (無ければ他の画面の一番新しいもの. 14 日より古いものは出さない) を「保存していない定義の下書きがあります」と出し, 「下書きを開く」か「下書きを捨てる」を選べる (開くと保存していない変更として開く. 今の変更がある場合は確かめる). 保存する名前の欄に打った, まだ保存していない名前も下書きに残し, 開くと欄に戻す (下書きは定義の変更を守るためのもので, 名前だけを変えた場合は残さない. 新規, 開く, 保存で打った名前を消す. 保存の間は下書きを開く・捨てるを止める). 聞いている間は前の下書きを上書きしない. 保存, 新規, 開く, 捨てる, 保存した時点と同じに戻した場合に, その画面の下書きを消す. 部品が外されるとき (殻の中で段階を移る, 同じ段階を押し直す) と, 殻で選んだ問題の設定 (`project`) が替わるときは, 保存していない変更を待たずに下書きに書く (殻の中の移動ではページを閉じないので `beforeunload` の確かめが出ず, 部品は移動を止められないため. 次に開いたときに下書きから戻せる). 戻すかを聞いている間に変えた定義も, そのときに書く. 聞いている下書きがこの画面のものなら, 上書きせずに別の画面の下書きとして書く (前の下書きと聞いている間の変更の両方を失わないため. 次に開くと前の下書きを先に聞き, 聞いている間の変更はその後に他の画面の下書きとして聞く). 聞き終えて今の変更をこの画面の下書きに書くと, 別に書いた下書きは消す
- **使えない部品の口**: ライブラリが無い部品と登録されていない部品のノードは, 定義のつなぎ先から口を推し量って (入力の口は inputs の名前, 出力の口は他から「ノード:口」で参照される名前) 線を描く (同梱の例をライブラリを入れずに開いても, つながりが見えるように)
- **置き場所と整列**: 新しく置くものは, 見えている範囲の真ん中の近くで他のノードと重ならない所に置く. 入力かノードを選んで部品を置くと, その右に置き (見えている範囲の外になる場合は, その位置に置いて表示を動かす), 置いた部品に必須の口か可変の数の口があれば, つなぎ元の最初の出力の口から最初の必須の口へ線を引く (出力が複数の部品も, 最初の口が主な出力 (`nn.MultiheadAttention` の `output`, `nn.LSTM` の `output` など). 参照は `ノード:口` になるので, 違えば詳細で選び直す. 出力が複数の部品から引かないと, 自己注意の後に置いた `op.Add` に注意の出力がつながらないまま誤り 0 件になるため). 他の口は, 同じ名前のモデルの入力 (GNN の `edge_index` など) があればそれにつなぐ. 出力を加えたとき, どこにもつながっていないノードが 1 つだけで出力の口が 1 つならそれにつなぐ. 置いた部品が選ばれるので, 続けて置くと一直線につながる (枝分かれさせる場合は, つなぎ元を選び直す). ノードの幅は整列の段の間隔に収まる上限 (236) までにし, 長い口の名前と形は省略してマウスを重ねると全体を出す. 整列 (後に全体が見えるように表示を合わせる) はつながりの深さで左から右へ段に分け (入力は最初, 出力は最後の段), 段が多い場合は折り返して下の行に続ける. 位置 (`ui`) の無い定義を開いた場合は, 位置の無いものにだけ同じ並べ方で位置を書く
- **読み上げと focus**: 先頭に「キャンバスへ移る」のリンク. ノードと線に日本語の読み上げの名前 (「ノード relu1 (nn.ReLU), 出力 out [4, 16]」「x から relu1 の input への線」). 明るさの切り替えは押した状態 (`aria-pressed`) を持つ. 詳細の欄の Esc は選んでいるノード (無ければキャンバス) に戻り, 消した後と Ctrl+S の後も focus を失わない. 全体のパラメータ数はマウスを重ねると正確な数
- **キーボード**: Ctrl+S (Mac は Cmd+S) で保存する (文字を打つ欄の中でも, 打ちかけの値を反映してから). Esc で編集している部分モデルから 1 つ上に戻る (押し続けても 1 つずつ). `/` で部品を探す欄に移る (Esc と `/` は文字を打つ欄の中では効かない). キーの操作 (保存, 元に戻す, 複製と写しなど) は根の部品の範囲 (`data-stage-root` の中) とどこにも focus が無いときだけ効き, 殻の上の帯で押したキーは扱わない (殻の欄の操作で定義を変えないため). React Flow が `document` で聞く Delete と Backspace (選んだ線とノードを消す) も同じで, 消す前 (`onBeforeDelete`) に focus のある所を見て, 範囲の外なら消さない. React Flow が聞く他のキー (Shift での範囲の選択, Space での移動など) は表示と選びだけで定義を変えないので, 範囲を見ない. 単独の起動では画面の全体が範囲の中なので, キーの操作は変わらない. 対話の枠などを `createPortal` で範囲の外に出さない (出すと, その中のキーを扱えなくなるため)
- **複製と写し**: 選んだ部品のノードを引数ごと複製し (Ctrl+D), 写して貼れる (Ctrl+C, Ctrl+V. アプリの中だけ). つなぎ先は写さない

### 部分モデル

- **写す**: 部品の一覧の「別の定義を部品にする」で, 保存した定義か同梱の例を今の定義の `subgraphs` に写し (ML-ModelControl の部分モデル), 一覧の「部分モデル」から `sub.<名前>` の部品として置く. 写した定義の入力が入力の口, 出力が出力の口になる. 参照ではなく写すので, 元の定義を後で変えても変わらない. 今開いている定義自身は選べない. 誤りのある定義を写す場合は, 誤りの数と最初の誤りを出して写すかを確かめる (確認だけで形は推定しない). 写した結果 (付け直した名前など) と消した結果は一覧の上に知らせる
- **名前**: 写した定義の名前. 同じ名前で中身の同じものは 1 つにまとめ, 中身の違うもの, Python の予約語, 書き出すコードのクラスの名前 (本体の `Model` と他の部分モデル) と重なるものは番号などを付けた名前にする (写す定義の中の部分モデルも同じく付け直し, 中の `sub.<名前>` も直す). 中身の比較では写した元を除く (写した元だけが違う同じ中身は 1 つにまとめる)
- **写し直す**: 写した元 (保存した定義か例の名前) を部分モデルの `ui.source` に書き, 一覧の写し直しのボタンで, 同じ名前のまま元の定義の今の中身に置き換える (元の定義を直した後に. 元に戻すで戻せる). 口が変わった場合は本体の誤りになる. 前の中身の位置は同じ名前のものに残し, 位置だけの違いは変わっていない扱い. 前の中身だけが使っていて使われなくなった部分モデルは消す. 写す定義の中に同じ名前の部分モデルがあれば番号を付けた名前にして, 自分を使う形にしない. 読み込みの間に定義が変わった場合は, その時点の定義に対して行い, 部分モデルが無くなっていれば何もしない. 今開いている定義自身からは写し直さない
- **消す**: 使っているノードの無い部分モデルは一覧から消せる (他の部分モデルの中で使っている場合は, そちらを先に消すように知らせる)
- **中身を読む**: 選んだ部分モデルのノードの詳細で, 中身 (入力の元の形, 中のノードの部品と引数, 出力) を読める. 部分モデルの中の誤りは, 定義全体の誤りとして場所 (`subgraphs.<名前>...`) 付きで出す
- **中身を編集する**: 部分モデルを使うノードの詳細の「部分モデルの中身を編集」かノードのダブルクリックで, その部分モデルを 1 つの定義としてキャンバスで編集する. キャンバスの上に階層 (本体 › sub.outer › sub.block. 入れ子で開ける) と, 使っているノードの数を出し, 階層の名前で戻る. 変更は定義の中の部分モデルに書き戻し, 元に戻すの履歴は本体と同じ (戻して部分モデルが無くなった場合は, あるところまで戻る). 置くと循環になる部品 (自分自身と, 中で自分を使う部分モデル) は一覧に出さず, 貼り付けもしない. 位置の無い部分モデルは編集を始めるときに位置を書く (履歴に残さず, 保存していない変更にもしない). 保存, Python の書き出し, 別の定義を部品にする, 部分モデルを消す操作は定義全体に対して行い, YAML の表示は編集している部分モデルの中身を出す
- **編集している間の確認**: 確認と形の推定はその部分モデルだけで行う (自分自身を除き, 中で使う部分モデルだけを持たせる). 本体の部分モデルを開いた場合は, 本体も形の推定をして, その部分モデルを使うノードを計算の順に見て, 全ての入力の口の形が分かる最初のノードに入る形を入力の形にして推定する (入力から来る値は入力の型と値の作り方, ノードから来る値は出力の型と 0. 保存する入力の形は変えない. 「形はノード x に入る形で推定」と出す). そのようなノードが無い場合と入れ子で開いた場合 (本体は確認だけ) は, 部分モデルの入力に書いた形で推定する. 本体の誤り (口の名前を変えて本体のつなぎ先が合わなくなった場合など) も確かめて「本体に誤り n 件」と出す
- **ノードだけの部分モデル**: 部分モデルを使うノードの詳細の「このノードだけの部分モデルにする」で, その部分モデルを写して `<元の名前>_<ノード>` の部分モデルにし (2 つ以上のノードが使う部分モデルだけ), そのノードだけが使うようにする (同じ部分モデルを重ねた中の 1 段だけチャンネル数を変える場合など). 写したものは写し直しの対象にしない

### 根の部品

画面のパッケージ (`frontend`) は, 段階の画面の根の部品 `StageApp` (`src/StageApp.tsx`) と, 段階に固有の CSS (`src/stage.css`) を公開する (`package.json` の `exports` の `.` と `./stage.css`). 殻は自分の画面のビルドにこの 2 つを取り込む (ML-Studio の設計の「画面: 根の部品」). 単独の起動では `main.tsx` が既定の値で `StageApp` を描く.

| props | 型 | 意味 | 単独の値 |
| --- | --- | --- | --- |
| `basename` | `string` | 画面の経路の頭 (例 `/model`). このアプリは経路を持たない 1 画面なので使わない (殻から見て他のアプリと同じ形にするため受け取る) | `""` |
| `apiBase` | `string` | API の頭 (例 `/api/model`). API の呼び出しは全てこの下 | `"/api"` |
| `project` | `string \| null` | 殻で選んだ問題の設定の識別子 (ML-Pathfinder の問題の設定の置き場の `<識別子>` ディレクトリの名前). null なら選んでいない | `null` |
| `onProjectChange` | `(project: string \| null) => void` | 「データセットとプロジェクト」で置き場の別の問題の設定から保存先を決めたときに, その識別子で呼ぶ | 何もしない |
| `onProjectsChange` | `() => void` | 呼ばない (このアプリは問題の設定を作らず, 消さず, 名前を変えないので, 一覧は変わらない) | 何もしない |
| `embedded` | `boolean` | 殻の下か. true なら上の操作のアプリの名前 (`h1`) と明るさの切り替えを出さない (上の操作の他のボタンは出す) | `false` |

- 部品は自分の TanStack Query の client を持つ. 経路を持たないのでルーターは持たない. API の頭は部品の中で 1 度決めて context で渡し, 画面の部品は `useApi()` で呼び出しの一式を取る (呼び出しごとに頭を渡し忘れないため)
- 画面のソースでは根から始まる絶対パスを使わない (殻の下では根が殻の画面を指すため). `index.html` の `/favicon.svg` は単独の起動のためのもの
- 画面の高さは親の高さ (`h-full`) に合わせる. 単独では `html`, `body`, `#root` が画面の高さで, 殻の下では殻の上の帯の下の高さになる (画面の高さに合わせると殻の帯の分はみ出すため)
- 明暗は `html` 要素のクラス `dark` と `localStorage` の `theme` で持つ. 単独では切り替えで両方を書き, `index.html` が描画の前に読む. `embedded` では書かずに読むだけにし, `html` のクラスの変化を見て読み直す (殻の切り替えで, テーマで色を変えるキャンバス (React Flow の `colorMode`) も描き直すため)
- `stage.css` は段階に固有の CSS (Tailwind の読み込みと色のトークン以外. 数の桁をそろえる `.tabular` と, キャンバスのノードと線の focus の枠. React Flow の CSS と読む順によらず勝つように, `.react-flow` を頭に付けて強くする). 単独では `index.css` が Tailwind と色のトークンと一緒に読む. React Flow の CSS は根の部品が読む (殻が別に取り込まずに済むように)

### 殻で選んだ問題の設定

殻のプロジェクトは問題の設定の識別子で, このアプリでは「データセットとプロジェクト」のダイアログの「問題の設定から選ぶ」の一覧 (`GET /api/problems`) のうち, 場所の親のディレクトリの名前が識別子のものに対応させる (識別子は置き場の `<識別子>/problem.yaml` のディレクトリの名前のため). その問題の設定の記録 (ML-Quest の `handoff` で読む学習のプロジェクトの記録とデータセットの場所) が既定になる.

- `project` があれば, ダイアログを開いたときに, その問題の設定を一覧から選んだのと同じく扱う (上の「データセットとプロジェクト」). 保存先を確かめ, 「プロジェクトに保存」の欄にその `problem.yaml`, 「データセットから入力と出力を作る」の欄に記録のデータセットの場所を入れ, 受け持ちに合う雛形があれば一覧から選んだときと同じ決まりで開くか選べるようにする. ダイアログの頭に「選んだ問題の設定」の欄を置き, 名前と識別子を出す. 開いている間に殻が選び直したら, 新しい問題の設定で同じように入れる. ただし確かめてある保存先が既にその問題の設定のもの (ダイアログが知らせた値を殻が受け付けて返したときなど) なら入れ直さない (確かめと雛形の知らせを重ねないため). ダイアログを開き直したときは, 一覧を読み込み済みでも同じように入れる
- 使えない問題の設定 (一覧の `usable` が偽) は理由を, 置き場に無い識別子は置き場に無いことを, 一覧を読めない場合はその理由を「選んだ問題の設定」の欄に出し, 欄には何も入れない (一覧か欄で選べる)
- 「開く」のダイアログの「学習の実験の定義の写し」の場所の欄も, この欄に打つ前なら, 選んだ問題の設定の記録のプロジェクトの場所にする
- ダイアログの中で, 置き場の別の問題の設定から保存先を決めたとき (一覧から選んだか, 置き場の `problem.yaml` を欄に書いて確かめた) は, その識別子で `onProjectChange` を呼ぶ. 識別子が `project` と同じなら呼ばない (殻と部品の間で知らせが行き来し続けないため). 置き場の外の問題の設定やプロジェクトのディレクトリから決めたときは, 同じ名前のディレクトリでも呼ばない (殻のプロジェクトに無い識別子を渡さないため). 前に確かめた保存先と同じ問題の設定を確かめ直したとき (名前を変えた, 保存が 409 で確かめ直したなど) も呼ばない (同じ知らせを重ねないため). 置き場にあるかは, 保存先の記録を読んだ問題の設定の場所 (`problem_path`) と一覧の場所 (どちらも実際のパス) を比べて決める
- `project` が null なら「選んだ問題の設定」の欄を出さず, 欄は今まで通り覚えた場所から始める

## 4. API

単独の起動では全て `/api` の下. 起動ごとのトークン (Cookie か `x-createarchitecture-token` ヘッダー) が要る. 殻の下では下の表の `/api` が殻の頭 (`/api/model`) に替わる.

### アプリの組み立て

API と, 確かめと画面の配信を, 2 つの FastAPI のアプリに分ける (殻の下では確かめを殻の 1 つだけにするため).

- `create_api(data_dir=None, *, problems_dir=None, modules=None)`: API だけのアプリ. 殻はこれを `/api/model` の頭の下に mount する
    - 4 つの router (`api`, `project`, `experiments`, `templates`) は全て頭なし (`APIRouter()`) で, このアプリに加える. mount の下の経路の照合は mount の頭を除いた経路で行われるため
    - トークン, Origin, ホスト名の確かめ, `/api/auth`, 画面の配信を持たない (載せる側が持つ). 仕様の画面 (`/docs`, `/redoc`, `/openapi.json`) も閉じる
    - 置き場は `app.state.store` (定義のファイル) と `app.state.problems_dir` (ML-Pathfinder の問題の設定の置き場), 読み込んだ自作の部品のモジュールは `app.state.custom_modules` に持ち, ルートは `request.app.state` から取る. Starlette では mount した sub-app の中の `request.app` は sub-app を指すので, 殻の下でもルートはそのまま動く
    - `data_dir` はこのアプリのデータの置き場 (無ければ既定の置き場. 下の「6. 置き場」). `problems_dir` は問題の設定の置き場. 渡さなければ作ったときの `ML_PATHFINDER_HOME` (無ければ既定) の下の `problems`. 殻は ML-Pathfinder と同じ置き場を渡す. `modules` は起動の設定の自作の部品のモジュール (無ければ `ML_CREATEARCHITECTURE_MODULES`. 上の「3. 画面」の「自作の部品 (起動の設定のモジュール)」)
    - lifespan と startup, shutdown の処理を使わず, 自作の部品のモジュールの読み込みも呼んだときに済ませる (mount した sub-app の lifespan は動かないため). 読み込めないモジュールがあれば `ValueError` で止める
    - 部品の登録簿 (ML-ModelControl の `REGISTRY`) はプロセスで 1 つで, 同じプロセスの他のアプリ (ML-Provide が ML-Inference を通して入れる自作の部品など) と共有する. 読み込み済みのモジュールは ML-ModelControl が前の結果を返すので, `create_api` を何度呼んでも, 他のアプリが先に同じモジュールを読み込んでいても重ねて登録しない. 部品の一覧 (`GET /api/units`) は登録簿の全ての部品を出し, `GET /api/modules` はこのアプリに渡したモジュールだけを出す
    - 呼ぶたびに新しいアプリを返す (テストと殻で別の置き場を渡せるように)
- `create_app(data_dir=None, token=None, allowed_hosts=None, modules=None)`: 単独で起動するアプリ. 確かめ (トークン, Origin, ホスト名), `/api/auth`, 画面の配信を持つ外側のアプリに, `create_api(data_dir, modules=modules)` を `/api` で mount する. 確かめは外側の middleware なので, mount した API にも効く. トークンを確かめないのは `GET /api/auth` だけ (他のメソッドの `/api/auth` も確かめる). `/api/auth` は mount より先に登録し, 画面の配信 (他のパスは index.html) は最後に置く. `/api` ちょうどと `/api/` の下の無いパスは画面でなく 404 を返す. 仕様の画面 (`/docs`, `/redoc`, `/openapi.json`) は外側のアプリでも閉じる (トークン無しで API の形を見せないため)
- 仕様の書き出し (`ml-createarchitecture --openapi`) は `create_api` の仕様のパスに `/api` を付けて書き出す (外側のアプリの仕様には mount した API が入らないため). 自作の部品のモジュールは読み込まない
- ポートはアプリが持たず, 起動の `ml-createarchitecture --port` (か殻) が決める

| `POST /api/project/experiment-spec` | 一覧の実験 (`run` と置き場 `root`) の定義の写しを読み, 保存する名前の候補と定義を返す. 置き場の 3 段を, 子のディレクトリの名前と `run` の名前を比べて辿り (送られた文字から場所を組み立てない), 無ければ 404, `root` を送らずに複数の置き場で `run` が重なれば 409, 開けないか, 別名や深い入れ子を含むか, 定義として読めない場合は 422 |

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| 部品 | モデルの 1 つの単位 (層, 演算, 外部のライブラリのモデルなど). ML-ModelControl の登録簿にあるもの |
| ノード | キャンバスに置いた部品の 1 つ. 名前, 引数の値, 入力のつなぎ先を持つ |
| 口 | ノードの入る口と出る口. 線は出る口から入る口へ引く |
| 定義 | モデルの入力, ノード, 出力をまとめたもの (ML-ModelControl の定義の形. YAML か JSON) |
| 部分モデル | 別の定義を, この定義の中で 1 つの部品 (`sub.<名前>`) として使うもの (定義の `subgraphs`) |
| 形の推定 | 入力の形から, 各ノードの出力の形とパラメータ数を求めること |

## 6. 置き場

既定は `~/.ml-createarchitecture/` (環境変数 `ML_CREATEARCHITECTURE_HOME` で変えられる).

- `models/<名前>.yaml`: 保存した定義. 名前はファイル名の規則 (英数字, `_`, `-`) に限り, 置き場の外には書かない
- 置き場の外に書くのは「プロジェクトに保存」の保存先だけ (下の「7. 安全」)
- 保存していない変更の下書きは置き場に置かず, ブラウザ (`localStorage`) に残す (上の「3. 画面」の「下書き」)
- 問題の設定の一覧は ML-Pathfinder の置き場 (`ML_PATHFINDER_HOME`. 無ければ `~/.ml-pathfinder`) の `problems/<識別子>/problem.yaml` を読む (2 つのアプリを同じ置き場で使うため, 環境変数も同じもの). 殻の下では `create_api` の `problems_dir` で問題の設定の置き場を渡す (上の「4. API」)

## 7. 安全

確かめ (トークン, Origin, ホスト名) と `/api/auth` は `create_app` の外側のアプリだけが持ち, `create_api` は持たない. 殻の下では殻が 1 つだけ持つ (段階ごとに確かめが重ならないように). `create_api` を確かめの無いアプリに載せて待ち受けない.

既定では `127.0.0.1` だけで待ち受ける (他のホストを指定すると警告を出す). 起動ごとのトークン (Cookie かヘッダー) を持つ要求だけを API で受け付け, 他のサイトからの書き込み (Origin が接続先と違うもの) と別のホスト名での接続を断る. 手元のファイルを読めるので, トークンは他の人に渡さない.

- 他のサイトから Hugging Face のモデルの取得などを起こされないように, 画面からの要求も全てトークンを確かめる
- 定義の名前はファイル名の規則に限り, 置き場の外には書かない. 外部の重みを読むのは定義の置き場と `ML_MODELCONTROL_WEIGHTS_DIRS` の中だけ (上の「4. API」の `POST /api/weights`)
- 自作の部品のモジュールは起動する人だけが選ぶ (上の「3. 画面」の「自作の部品 (起動の設定のモジュール)」)
- 「プロジェクトに保存」で書くのは, 拡張子が小文字の `.yaml` か `.yml` の保存先 1 つだけ. 名前で選ぶ保存先はプロジェクトの `models/` の直下に限り, リンクには書かない. config (`model.spec`) は書き換えない. 問題の設定の記録の保存先はプロジェクトの場所の中に限り, 学習の設定 (`configs/` の中), 問題の設定の写し (直下の `problem.yaml`), データと実験 (`data/` と `outputs/` の中) には書かず, 作るディレクトリもプロジェクトの中だけ. 既にあるファイルは確かめてから上書きし, 上書きの許しは確かめた保存先にだけ効かせる. 書く前に定義として読めることと, 問題の設定から決めた保存先では骨組みの入力と出力に合うこと (合わなければ利用者が選んだ場合だけ書く) を確かめ, 一時ファイルに書いてから置き換える. 場所は絶対のパス (`~` から書ける) だけを受け取る
- 実験の定義の写しを読むのは, プロジェクトの中で途中にリンクの無い実験の置き場の, 一覧に出す実験の `model_spec.yaml` (リンクでない普通のファイル, 16 MiB まで) だけ. 読むだけで, 実験のディレクトリには書かない

## 8. 課題の型への広げ方

部品と定義の形は ML-ModelControl に足し, この画面はそれを使う (受け持ちごとの雛形は「開く」の同梱の例, 定義の版 2 は「パラメータの状態」, 定義の版 3 は「引数に書く部品」, 学習済みの重みは「学習済みの重みのライセンス」, 研究の自作の部品は「自作の部品 (起動の設定のモジュール)」).
